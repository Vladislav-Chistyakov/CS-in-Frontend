# AI конспект для лекции #2

## Повторение: процессор и его операции

Процессор выполняет простые операции: сложение, вычитание, чтение из памяти, запись в память, сравнение, переходы. Все
эти операции закодированы числами — **опкодами** (operation codes). Процессор не знает, что такое "переменная" или "функция" — он просто получает на вход поток байтов (инструкции и данные) и выполняет их последовательно.

**Как процессор понимает, какую инструкцию выполнить?**

У процессора есть специальный регистр — **счётчик команд** (program counter, PC). Он хранит адрес текущей инструкции в
памяти. Процессор читает байт по этому адресу, интерпретирует его как опкод, выполняет соответствующую операцию, затем
увеличивает счётчик и переходит к следующей инструкции.

### Как процессор загружается

При включении компьютера процессор начинает выполнять код с фиксированного адреса в памяти (например, 0xFFFFFFF0). По
этому адресу находится BIOS или UEFI — небольшая программа, прошитая в материнской плате. Она инициализирует
оборудование, проверяет память, затем загружает загрузчик с диска, а загрузчик уже запускает операционную систему.

Весь этот путь — от BIOS до запущенного браузера — это цепочка программ, каждая из которых загружает следующую. И все
они в конечном счёте представляют собой последовательности машинных инструкций.

## Зачем нужны языки программирования?

Писать программы напрямую в машинных кодах — крайне трудоёмко. Каждая операция кодируется числом, нужно вручную
управлять регистрами и адресами памяти, легко ошибиться, а код получается непереносимым между архитектурами.

Языки программирования позволяют:

- Писать в понятной человеку форме (словами, выражениями)
- Использовать имена для переменных и функций
- Не думать о регистрах и адресации напрямую
- Абстрагироваться от конкретной архитектуры процессора

### Машинный код

Машинный код — это последовательность байтов, которую процессор может выполнять напрямую. Каждая инструкция — это
опкод (1–3 байта) и операнды (данные или адреса).

```x86
B8 01 00 00 00    ; загрузить число 1 в регистр EAX
```

Человеку читать и писать такой код очень сложно.

### Языки ассемблера

Ассемблер — это "человекочитаемая" обёртка над машинным кодом. Вместо `B8` пишется `mov eax, 1`. Каждая инструкция
ассемблера соответствует одной машинной инструкции.

```x86asm
mov eax, 1
add eax, 2
cmp eax, 3
jz label
```

Ассемблер привязан к архитектуре: x86-ассемблер не подойдёт для ARM. Но он даёт полный контроль над процессором и
позволяет писать очень эффективный код.

**Плюсы ассемблера:**

- Максимальная производительность (можно использовать все возможности процессора)
- Полный контроль над памятью и регистрами
- Возможность писать код для железа без операционной системы (микроконтроллеры, загрузчики, ядра ОС)

**Минусы ассемблера:**

- Низкая скорость разработки
- Высокий порог входа
- Код непереносим между архитектурами
- Сложность поддержки и отладки

### Исполняемые файлы и операционная система

Исходный код на ассемблере или другом языке превращается в **исполняемый файл**. Это не просто набор машинных
инструкций — у него есть определённая структура, которую понимает операционная система.

**Форматы исполняемых файлов:**

- **PE (Portable Executable)** — для Windows (.exe, .dll)
- **ELF (Executable and Linkable Format)** — для Linux и Unix
- **Mach-O** — для macOS

Внутри такого файла есть:

- Заголовок с метаинформацией (какая архитектура, точка входа)
- Сегменты кода (инструкции)
- Сегменты данных (константы, инициализированные переменные)
- Таблицы импорта/экспорта (какие функции из DLL/SO нужны)

Операционная система загружает файл в память, выделяет под него адресное пространство, настраивает права доступа (чтение, запись, исполнение) и передаёт управление на точку входа.

#### Обратная совместимость ОС

Обратная совместимость — сложная тема. В Windows, например, нельзя взять исполняемый файл от Windows 3.1 или Windows 95 и запустить его на Windows 11 напрямую. Форматы исполняемых файлов и системные вызовы менялись кардинально.

Для запуска старых программ используются:

- **Режим совместимости** — эмуляция старых версий API на уровне ОС
- **Виртуализация** — запуск старой ОС внутри виртуальной машины
- **Эмуляторы** (о которых речь пойдёт дальше)

В мире Linux обратная совместимость на уровне системных вызовов сохраняется лучше, но и там бывают проблемы с устаревшими библиотеками.

#### Эмуляция для старых программ

Если программа была скомпилирована для другой архитектуры (например, x86-программа на ARM-процессоре), операционная
система не может её запустить напрямую. Для этого используются **эмуляторы** — программы, которые имитируют работу
другой архитектуры.

Примеры:

- **Wine** — запуск Windows-программ на Linux (эмуляция Windows API)
- **QEMU** — эмуляция целых процессоров (x86 на ARM, ARM на x86)
- **Rosetta** на macOS — эмуляция x86-программ на Apple Silicon (ARM)

Эмуляция работает медленнее нативного выполнения, так каждая инструкция превращается в десятки инструкций эмулятора. Но
для многих задач этого достаточно.

### Неисполняемые файлы

Не все файлы содержат исполняемый код. Есть:

- **Скрипты** (`.js`, `.py`, `.sh`) — их исполняет интерпретатор
- **Байткод** (`.class` для Java, `.wasm` для WebAssembly) — исполняется виртуальной машиной
- **Данные** (`.txt`, `.jpg`, `.mp4`) — не содержат инструкций, только информацию

Фронтенд-разработчику важно понимать, что JavaScript-файлы — это не исполняемые файлы в смысле ОС. Они не содержат
машинных инструкций для процессора. Их выполняет JavaScript-движок (V8, SpiderMonkey), который сам является исполняемым
файлом.

### Зачем фронтенд-разработчику знать ассемблер?

Казалось бы, веб-разработка далека от низкоуровневого программирования. Но знание ассемблера и устройства процессора
помогает:

- Понимать, как работают эмуляторы в браузере (например, для запуска старых игр)
- Понимать, как компилируются языки в WebAssembly
- Понимать, как JIT-компиляторы (V8) оптимизируют JavaScript
- Писать более производительный код, понимая "цену" тех или иных операций

### Эмуляция x86 на JavaScript

Существуют проекты, которые эмулируют процессор x86 на JavaScript прямо в браузере. Например:

- **Windows 3.1 в браузере** — полноценная эмуляция старой ОС
- **Windows 95 в браузере** — аналогично, с возможностью запускать Internet Explorer

Эти эмуляторы работают так: JavaScript-код интерпретирует x86-инструкции, эмулирует память, регистры, прерывания,
видеокарту. Это медленно, но для старых игр (Doom, SimCity) производительности хватает.

## Языки высокого уровня

Ассемблер слишком низкоуровнев для большинства задач. Поэтому появились языки высокого уровня, которые предоставляют:

- Переменные с именами
- Функции и процедуры
- Управляющие конструкции (if, for, while)
- Структуры данных (массивы, объекты)
- Абстракции (классы, интерфейсы, замыкания)

**Пример на Rust:**

```rust
fn main() {
    let x = 5;
    let y = 10;
    let sum = x + y;
    println!("Сумма: {}", sum);
}
```

Компилятор превращает этот код в машинные инструкции. Программист не думает о регистрах, но при этом код эффективен,
потому что Rust позволяет контролировать память без сборщика мусора.

### Контракты языков программирования

Каждый язык программирования накладывает **контракты** — правила, которые должен соблюдать программист, и гарантии,
которые даёт язык.

Примеры контрактов:

- **C/C++:** ты управляешь памятью сам. Гарантия: максимальная производительность. Риск: ошибки с памятью (use-after-free, утечки).
- **Java/Rust:** память управляется автоматически (сборщик мусора или система владения). Гарантия: безопасность памяти.
  Цена: возможные паузы (GC) или сложность обучения (Rust).
- **Python/JS:** динамическая типизация. Гарантия: гибкость и скорость разработки. Цена: ошибки в рантайме и меньшая
  производительность.

Выбор языка — это выбор набора контрактов под конкретную задачу.

### Как программа исполняется: компиляция и интерпретация

Существует два основных подхода к выполнению кода: **компиляция** и **интерпретация**.

#### Компиляция и компиляторы

**Компилятор** — это программа, которая переводит исходный код (на языке высокого уровня) в машинный код (или другой
целевой формат) до начала выполнения.

**Этапы компиляции:**

1. Лексический анализ (разбор на токены)
2. Синтаксический анализ (построение AST)
3. Семантический анализ (проверка типов и т.д.)
4. Генерация промежуточного кода (байткод, IR)
5. Оптимизация
6. Генерация машинного кода

**Оптимизации компилятора:**

- Вычисление констант на этапе компиляции
- Удаление мёртвого кода
- Инлайнинг функций (вставка тела функции вместо вызова)
- Перестановка инструкций для конвейера процессора

**Важно:** компилятор не исправляет неправильные алгоритмы. Если алгоритм квадратичный, компилятор не сделает его
линейным. Он может только улучшить реализацию.

**Пример оптимизации (вычисление констант):**

```c
int x = 5;
int y = 10;
int z = x + y;  // компилятор сразу заменит на z = 15
```

**Явная фаза компиляции:** в языках типа C, C++, Rust, Go компиляция происходит до запуска программы. Получается
исполняемый файл, который можно распространять и запускать без исходников.

#### Интерпретация и интерпретаторы

**Интерпретатор** — это программа, которая читает исходный код и выполняет его построчно, без предварительной компиляции
в машинный код.

**Пример интерпретатора на JavaScript:**

```js
function interpret(program) {
	const lines = program.split('\n');
	for (const line of lines) {
		if (line.startsWith('print')) {
			const message = line.slice(6);
			console.log(message);
		}
// ... другие команды
	}
}
```

**Плюсы интерпретации:**

- Не нужно ждать компиляции (быстрый старт)
- Легче писать REPL (Read-Eval-Print Loop)
- Проще переносимость (нужен только интерпретатор)
- Можно выполнять код, который генерируется на лету (eval)

**Минусы интерпретации:**

- Медленнее, чем скомпилированный код
- Каждый раз при запуске нужно разбирать исходный код
- Ошибки типов проявляются только во время выполнения

### Интерпретатор vs компиляция: сравнение

| Характеристика      | Компиляция                    | Интерпретация                                 |
|---------------------|-------------------------------|-----------------------------------------------|
| Скорость выполнения | Высокая                       | Низкая (каждая инструкция разбирается заново) |
| Старт программы     | Медленный (компиляция)        | Быстрый (сразу выполнение)                    |
| Переносимость       | Низкая (нужна перекомпиляция) | Высокая (нужен интерпретатор)                 |
| Оптимизации         | Глобальные, много времени     | Ограниченные (на лету)                        |
| Распространение     | Бинарный файл                 | Исходный код + интерпретатор                  |

### Байткод и виртуальные машины

Компромисс между компиляцией и интерпретацией — **байткод** (промежуточное представление) и **виртуальная машина** (VM),
которая его исполняет.

**Схема работы:**

1. Компилятор превращает исходный код в байткод (не машинный!)
2. Виртуальная машина интерпретирует байткод или компилирует его на лету

**Пример виртуальной машины на JavaScript:**

```js
const program = [
	{op: 'PUSH', value: 42},
	{op: 'PRINT'},
	{op: 'HALT'}
];

function execute(program) {
	for (const instr of program) {
		switch (instr.op) {
			case 'PUSH':
				stack.push(instr.value);
				break;
			case 'PRINT':
				console.log(stack.pop());
				break;
			case 'HALT':
				return;
		}
	}
}
```

**Опкоды (коды операций):**

В реальных виртуальных машинах (Java VM, .NET CLR, WebAssembly) инструкции кодируются числами для компактности и
скорости. Виртуальная машина получает массив чисел (байткод) и выполняет соответствующие действия.

#### Кэширование байткода

Чтобы не компилировать исходный код в байткод при каждом запуске, его можно **кэшировать**. При повторном запуске той же функции используется уже готовый
байткод.

**Кэширование** — это универсальная оптимизация, которая применяется везде: от процессоров (кэш-память) до
веб-браузеров (кэш HTTP).

#### Почему процессор не исполняет байткод напрямую?

Байткод — это абстракция, придуманная для переносимости. Разные процессоры (x86, ARM, RISC-V) понимают разные наборы
инструкций. Если бы процессоры исполняли байткод Java напрямую, то:

- Байткод пришлось бы менять при смене архитектуры
- Процессоры стали бы сложнее и дороже
- Переносимость исчезла бы

Поэтому байткод исполняется виртуальной машиной, а VM уже транслирует его в машинный код конкретного процессора.

### AOT и JIT компиляция

#### AOT (Ahead-of-Time) компиляция

Код компилируется в машинный код **до** запуска программы (отдельная фаза или непосредственно перед запуском).

**Примеры:** C, C++, Rust, Go, а также WebAssembly (компилируется заранее в .wasm).

**Плюсы AOT:**

- Высокая производительность с самого начала
- Нет накладных расходов на компиляцию во время выполнения
- Компактные исполняемые файлы (не нужен интерпретатор)

**Минусы AOT:**

- Нельзя оптимизироваться под конкретные данные во время выполнения
- Дольше время сборки

#### JIT (Just-In-Time) компиляция

Код компилируется в машинный код **во время выполнения** программы.

**Схема работы JIT:**

1. Интерпретатор начинает выполнять код (быстрый старт)
2. "Горячие" участки (выполняемые много раз) компилируются в машинный код
3. Скомпилированный код выполняется быстрее

**Примеры:** Java (HotSpot), C# (.NET), JavaScript (V8, SpiderMonkey), LuaJIT.

**Преимущество JIT:**

- Можно собирать профилировочную информацию во время выполнения и оптимизироваться под реальные данные
- Например, если функция всегда вызывается с числами, JIT сгенерирует код для чисел (а не для общего случая)

**Минусы JIT:**

- **Прогрев кода (warm-up):** сначала код выполняется медленно (интерпретация), потом быстрее (JIT-компиляция)
- Дополнительное потребление памяти (хранится и интерпретатор, и скомпилированный код)
- **Деоптимизация (deopt):** если предположение JIT не оправдалось (например, пришёл аргумент другого типа), нужно
  откатиться на интерпретатор — это дорого

#### Динамическая типизация и JIT

JavaScript — язык с динамической типизацией. Это усложняет JIT-компиляцию:

```js
function add(a, b) {
	return a + b;
}

add(1, 2);             // числа → генерация кода для чисел
add("hello", "world"); // строки → ой, предположение не сработало, деоптимизация!
```

JIT-компилятор пытается угадать типы на основе первых вызовов. Если типы меняются, приходится деоптимизироваться и
перекомпилировать.

#### Как увидеть работу JIT

В Chrome DevTools (Performance) можно включить профилирование и увидеть:

- Время, потраченное на компиляцию
- Когда срабатывает оптимизация
- Когда происходит деоптимизация

#### Архитектура V8 (движок JavaScript в Chrome)

V8 использует **несколько JIT-компиляторов**:

1. **Ignition** — интерпретатор байткода (быстрый старт)
2. **Sparkplug** — быстрый JIT (компилирует без сложных оптимизаций)
3. **Maglev** — оптимизирующий JIT (средний уровень)
4. **Turbofan** — супер-оптимизирующий JIT (максимальная производительность для "горячего" кода)

**Почему столько уровней?** Каждый уровень даёт прирост производительности, но требует времени на компиляцию. Чем "горячее" код, тем больше ресурсов в него вкладывается.

##### Почему Chrome потребляет много памяти?

- Хранит несколько версий кода (интерпретируемый байткод + скомпилированный машинный код)
- Кэширует байткод
- Держит в памяти профилировочную информацию
- У каждого вкладки свой процесс со своим движком V8

Это цена за производительность и изоляцию.

## Виртуальная машина и экосистема

**Виртуальная машина (VM)** — это программа, которая исполняет байткод. Но VM — это не только исполнитель. В экосистему
входят:

- **Компилятор** (исходный код → байткод)
- **Интерпретатор / JIT** (байткод → выполнение)
- **Сборщик мусора** (управление памятью)
- **Стандартная библиотека** (встроенные функции)
- **Инструменты** (отладчик, профилировщик)

**Примеры виртуальных машин:**

- **JVM** (Java Virtual Machine) — для Java, Kotlin, Scala
- **CLR** (Common Language Runtime) — для C#, F#, VB.NET
- **V8** — для JavaScript и WebAssembly
- **Erlang VM** (BEAM) — для Erlang, Elixir

### Рантайм (runtime)

**Рантайм** — это среда выполнения программы. Она включает:

- Виртуальную машину (если есть)
- Системные библиотеки (libc, WinAPI)
- Сборщик мусора (для языков с GC)
- Модель многопоточности

В JavaScript рантайм включает:

- Движок (V8, SpiderMonkey, JavaScriptCore)
- Web API (DOM, fetch, setTimeout) — в браузере
- Node.js API (fs, http, crypto) — в Node.js

## Типы данных и типизация в языках программирования

### Встроенные типы

**JavaScript:**

```js
let a = 5;           // number
let b = 3.14;        // number (тоже)
let c = "hello";     // string
let d = true;        // boolean
let e = null;        // null
let f = undefined;   // undefined
let g = Symbol();    // symbol
let h = 42n;         // bigint
let i = {};          // объект
let j = [];          // массив (тоже объект)
```

### Виды типизации

| Тип типизации            | Описание                                               | Примеры языков                       |
|--------------------------|--------------------------------------------------------|--------------------------------------|
| **Статическая**          | Типы известны на этапе компиляции                      | C, Java, Rust, TypeScript            |
| **Динамическая**         | Типы проверяются во время выполнения                   | Python, JavaScript, Ruby             |
| **Сильная**              | Нельзя смешивать типы без явного преобразования        | Python, Rust, Java                   |
| **Слабая**               | Типы автоматически приводятся                          | JavaScript, C (в некоторых случаях)  |
| **Явная**                | Типы нужно указывать в коде                            | C, Java, Rust                        |
| **Неявная**              | Типы выводятся компилятором                            | Haskell, TypeScript (частично)       |
| **Утиная (duck typing)** | "Если выглядит как утка и крякает как утка — это утка" | Python, JavaScript, Go (interface{}) |
| **Структурная**          | Тип совместим, если структура совпадает                | TypeScript, Go (interface{})         |

### JavaScript: неявная, слабая, динамическая, утиная

**Неявное приведение типов (слабая типизация):**

```js
0 + null;          // 0 (null стал 0)
0 + undefined;     // NaN
"5" + 3;           // "53" (конкатенация)
"5" - 3;           // 2 (преобразовалось в числа)
!!"hello";         // true (приведение к boolean)
if ("") {
}                  // false (пустая строка)
```

**Динамическая типизация:**

```js
let x = 5;
x = "теперь я строка";  // ок, тип изменился
```

**Утиная типизация:**

```js
function quack(obj) {
	if (typeof obj.quack === 'function') {
		obj.quack();  // не важно, что за объект, главное — есть метод quack
	}
}
```

### Что даёт типизация

**Статическая типизация:**

- Ошибки типов ловятся на этапе компиляции
- Лучшая производительность (компилятор может оптимизировать)
- Лучшая поддержка IDE (автодополнение, рефакторинг)
- Самодокументируемый код

**Динамическая типизация:**

- Быстрое прототипирование
- Меньше кода (не нужно писать типы)
- Гибкость (можно легко менять типы)

### Эффективность статической типизации

Компилятор, зная тип переменной, может:

- Выбрать оптимальные инструкции (для чисел, для строк)
- Выделить ровно столько памяти, сколько нужно
- Встроить (inline) функции, зная типы аргументов

В динамических языках всё это определяется в рантайме, что добавляет накладные расходы.

### Проблемы слабой типизации

Слабая типизация (как в JavaScript) может приводить к неожиданным ошибкам:

```js
[] + [];           // "" (пустая строка)
[] + {};           // "[object Object]"
{
}
+[];               // 0 (странное поведение)
"1" + 1;           // "11"
"1" - 1;           // 0
```

Поэтому в больших проектах на JavaScript часто используют **TypeScript** — надстройку, добавляющую статическую
типизацию.

# Итоги лекции

1. **Машинный код и ассемблер** — основа работы компьютера. Процессор выполняет простые операции, закодированные
   числами.

2. **Языки высокого уровня** предоставляют абстракции, чтобы программист не думал о регистрах и адресации. Каждый язык —
   это набор контрактов.

3. **Компиляция** превращает код в машинный до запуска. **Интерпретация** выполняет код построчно. Компромисс — *
   *байткод и виртуальная машина**.

4. **JIT-компиляция** (V8, JVM) компилирует "горячий" код на лету, давая высокую производительность при гибкости
   динамических языков. Цена — прогрев и деоптимизации.

5. **Типизация** бывает статической/динамической, сильной/слабой. Выбор типа типизации — это инженерное решение,
   влияющее на производительность, безопасность и удобство разработки.
