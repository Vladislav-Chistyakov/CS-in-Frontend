## Повторение: обычные массивы в JavaScript

Обычные массивы в JS — это гибридные структуры:

- Могут хранить элементы любых типов (числа, строки, объекты, другие массивы)
- Могут динамически менять размер
- Могут быть разреженными (с дырками)
- Каждый элемент — это полноценное JS-значение со всеми накладными расходами

```javascript
// Обычный массив — гибкий, но "тяжёлый"
const regularArray = [1, "hello", {name: "Alice"}, [1, 2, 3]];
regularArray.push(42);
regularArray[100] = "sparse";  // Дырки с 5 по 99 индекс
console.log(regularArray.length); // 101
```

## Типизированные массивы

### Что это такое?

Типизированные массивы — это механизм для работы с бинарными данными в JavaScript. Они представляют собой *
*представление (view) над непрерывной областью памяти (ArrayBuffer)** с фиксированным типом элементов.

В отличие от обычных массивов:

- Все элементы одного типа (Uint8, Int32, Float64 и т.д.)
- Размер фиксирован (нельзя расширить)
- Не может быть разреженным (нет дырок)
- Элементы занимают ровно столько байт, сколько нужно для их типа

### Смысл и профит типизированных массивов

**Зачем они нужны?**

1. **Экономия памяти.** Число в типизированном массиве занимает ровно столько байт, сколько нужно (4 байта для int32, 8
   для float64). В обычном массиве каждое число — это полноценный JS-объект с накладными расходами (обычно 8+ байт плюс
   ссылка).

2. **Скорость.** Доступ к элементам и числовые операции быстрее благодаря отсутствию проверок типов и лучшей локальности
   данных (кэш-дружественность).

3. **Работа с бинарными данными.** Позволяют читать/писать бинарные форматы (изображения, аудио, файлы, сетевые
   протоколы) напрямую.

4. **Совместимость с Web API.** Многие современные API (WebGL, WebAudio, Fetch, Canvas, WebRTC) работают с
   типизированными массивами.

```javascript
// Обычный массив чисел — тяжеловесный
const normalNumbers = [1, 2, 3, 4, 5];
// Каждое число — объект ~8-16 байт + ссылка ~8 байт = ~80-120 байт на 5 чисел

// Типизированный массив — компактный
const typedNumbers = new Int32Array([1, 2, 3, 4, 5]);
// 5 × 4 байта = 20 байт (в 4-6 раз меньше!)
```

### Виды типизированных массивов

В JavaScript существуют следующие типизированные массивы:

| Конструктор         | Тип элемента                          | Размер в байтах | Диапазон / особенности  |
|---------------------|---------------------------------------|-----------------|-------------------------|
| `Int8Array`         | 8-битное целое со знаком              | 1               | -128 до 127             |
| `Uint8Array`        | 8-битное целое без знака              | 1               | 0 до 255                |
| `Uint8ClampedArray` | 8-битное целое без знака (с зажатием) | 1               | 0 до 255 (clamp)        |
| `Int16Array`        | 16-битное целое со знаком             | 2               | -32,768 до 32,767       |
| `Uint16Array`       | 16-битное целое без знака             | 2               | 0 до 65,535             |
| `Int32Array`        | 32-битное целое со знаком             | 4               | -2³¹ до 2³¹-1           |
| `Uint32Array`       | 32-битное целое без знака             | 4               | 0 до 2³²-1              |
| `Float16Array`      | 16-битное число с плавающей точкой    | 2               | ~±6.10e-5 до ~±65,504   |
| `Float32Array`      | 32-битное число с плавающей точкой    | 4               | ~±1.2e-38 до ~±3.4e38   |
| `Float64Array`      | 64-битное число с плавающей точкой    | 8               | ~±5.0e-324 до ~±1.8e308 |
| `BigInt64Array`     | 64-битное целое со знаком             | 8               | -2⁶³ до 2⁶³-1           |
| `BigUint64Array`    | 64-битное целое без знака             | 8               | 0 до 2⁶⁴-1              |

```javascript
// Примеры разных типов
const int8 = new Int8Array([127, 128]);      // [127, -128] (переполнение)
const uint8 = new Uint8Array([255, 256]);    // [255, 0] (переполнение)
const clamped = new Uint8ClampedArray([255, 256, -1]); // [255, 255, 0] (зажатие)
const float32 = new Float32Array([1.123456789]); // 1.1234568 (округление)
```

### Запись и чтение

Чтение и запись элементов происходит так же, как в обычных массивах — через квадратные скобки.

```javascript
const arr = new Int32Array(5);

// Запись
arr[0] = 10;
arr[1] = 20;
arr[2] = 30;

// Чтение
console.log(arr[0]); // 10
console.log(arr[1]); // 20

// Ошибка — нельзя расширить
arr[10] = 100; // Не увеличит массив, просто проигнорирует (без ошибки)
```

### Конвертация типов при записи и чтении

Ключевой момент: в JavaScript существует всего два числовых типа: Number (64-битное число с плавающей точкой IEEE 754) и BigInt. Однако типизированные массивы хранят числа в своих специфичных форматах (Int8, Uint16, Float32 и т.д.). При каждом взаимодействии происходит неявное преобразование.

#### При записи: JS Number/BigInt → Тип массива

Когда вы присваиваете значение элементу типизированного массива, JS число преобразуется в формат массива:

```javascript
const int8 = new Int8Array(3);

int8[0] = 3.14; // 3.14 → 3 (дробная часть отбрасывается)
int8[1] = 3.9; // 3.9 → 3 (не округление, а отбрасывание)
int8[2] = -3.14; // -3.14 → -3

console.log(int8); // [3, 3, -3]
```

```javascript
const uint8 = new Uint8Array(3);

uint8[0] = 255; // 255 → 255 (максимум)
uint8[1] = 256; // 256 → 0 (переполнение: 256 % 256 = 0)
uint8[2] = -1; // -1 → 255 (256 + (-1) = 255)

console.log(uint8); // [255, 0, 255]
```

```javascript
const float32 = new Float32Array(2);

float32[0] = 1.234567891011; // Округление до 6-7 знаков
float32[1] = 1e50; // 1e50 → Infinity

console.log(float32); // [1.2345679, Infinity]
```

```javascript
// Нечисловые значения
const int32 = new Int32Array(3);
int32[0] = "123"; // "123" → 123
int32[1] = "abc"; // "abc" → NaN → 0
int32[2] = null; // null → 0

console.log(int32); // [123, 0, 0]
```

#### При чтении: Тип массива → JS Number/BigInt

При чтении значения из типизированного массива данные преобразуются обратно в стандартный JS Number/BigInt.

```javascript
const int8 = new Int8Array([255, 128, -1]);
console.log(int8[0]); // -1 (255 в Int8 превращается в -1)
console.log(int8[1]); // -128
console.log(int8[2]); // -1

const uint8 = new Uint8Array([255, 128, -1]);
console.log(uint8[0]); // 255
console.log(uint8[1]); // 128
console.log(uint8[2]); // 255 (-1 превратился в 255 при записи)
```

```javascript
const int32 = new Int32Array([0xFFFFFFFF]);
console.log(int32[0]); // -1 (0xFFFFFFFF как знаковое 32-битное = -1)

const uint32 = new Uint32Array([0xFFFFFFFF]);
console.log(uint32[0]); // 4294967295 (беззнаковая интерпретация)
```

#### Важное следствие: потеря информации

Из-за преобразований информация может быть потеряна в обе стороны:

```javascript
// Потеря при записи: число вне диапазона
const uint8 = new Uint8Array(1);
uint8[0] = 1000;
console.log(uint8[0]); // 232 (а не 1000)

// Потеря при записи: дробное число в целочисленный массив
const int32 = new Int32Array(1);
int32[0] = 3.14;
console.log(int32[0]); // 3 (потеряли .14)

// Потеря точности: Float64 → Float32 → Float64
const float32 = new Float32Array(1);
float32[0] = 1.23456789;
const readBack = float32[0];
console.log(readBack); // 1.2345679 (чуть отличается)
console.log(readBack === 1.23456789); // false
```

## ArrayBuffer — основа всего

### Что такое ArrayBuffer?

`ArrayBuffer` — это **сырой непрерывный блок памяти** (область байт). Сам по себе он не предоставляет способа читать или
записывать данные — это просто "кусок памяти".

```javascript
// Создание буфера на 16 байт
const buffer = new ArrayBuffer(16);
console.log(buffer.byteLength); // 16
// buffer[0] = 42 — НЕ РАБОТАЕТ!
// ArrayBuffer нельзя читать/писать напрямую
```

### Способы создания типизированного массива

1. С указанием длины:

    ```javascript
    const arr1 = new Int32Array(10);  // 10 элементов, все = 0
    ```

2. Из существующего массива:

    ```javascript
    const arr2 = new Int32Array([1, 2, 3, 4, 5]);  // Копирует данные
    ```

3. Из другого типизированного массива:

    ```javascript
    const source = new Int16Array([1, 2, 3]);
    const arr3 = new Int32Array(source);  // Копирует с преобразованием типов
    ```

4. На основе итератора:

    ```javascript
    const arr4 = Int32Array.of(...new Set([1, 2, 3]));
    ```

5. На основе ArrayBuffer:

    ```javascript
    const buffer = new ArrayBuffer(16);
    const arr4 = new Int32Array(buffer);     // 4 элемента (16 / 4 = 4)
    const arr5 = new Int8Array(buffer);      // 16 элементов (другой view)
    ```

### Создание на основе ArrayBuffer со сдвигом и длиной

Можно создать view только на часть буфера:

```javascript
const buffer = new ArrayBuffer(16);
const arr = new Int32Array(buffer, 4, 3);
// Начинаем с байта 4 (пропустили 4 байта)
// 3 элемента по 4 байта = 12 байт
// Итог: arr использует байты 4-15 буфера
```

### Изменение размера ArrayBuffer

`ArrayBuffer` может изменять свой размер через метод `resize()` (если был создан с опцией `maxByteLength`).

```javascript
// Создаём буфер с возможностью расширения до 64 байт
const buffer = new ArrayBuffer(16, {maxByteLength: 64});
console.log(buffer.byteLength); // 16

// Расширяем
buffer.resize(32);
console.log(buffer.byteLength); // 32

// Уменьшаем
buffer.resize(8);
console.log(buffer.byteLength); // 8
```

### Fetch API и ArrayBuffer

`fetch` может получать данные напрямую как ArrayBuffer:

```javascript
const response = await fetch("https://example.com/image.png");
const buffer = await response.arrayBuffer();  // Получаем сырые байты файла

// Теперь можем интерпретировать эти байты
const uint8View = new Uint8Array(buffer);
console.log("Первые 5 байт файла:", uint8View.slice(0, 5));
```

### Чтение файлов пользователя через FileReader API

```javascript
const input = document.querySelector('input[type="file"]');

input.addEventListener("change", (event) => {
    const file = event.target.files[0];
    const reader = new FileReader();

    reader.onload = () => {
        const buffer = reader.result;  // ArrayBuffer
        const bytes = new Uint8Array(buffer);
        console.log("Размер файла в байтах:", bytes.length);
    };

    reader.readAsArrayBuffer(file);
});
```

## Концепция view (представлений)

### ArrayBuffer как представление всей памяти компьютера

`ArrayBuffer` можно представить как **уменьшенную модель всей оперативной памяти компьютера**. Это просто непрерывная
область байт. Чтобы работать с этими байтами как с числами, строками или сложными структурами, нужны **представления (
views)**.

### Множество потребителей для одного буфера

Один и тот же `ArrayBuffer` может иметь несколько представлений (views). Они все смотрят на одну и ту же область памяти.

```javascript
const buffer = new ArrayBuffer(8);

// Два разных представления на одном буфере
const int32View = new Int32Array(buffer);  // 2 элемента (4 байта каждый)
const int16View = new Int16Array(buffer);  // 4 элемента (2 байта каждый)
const uint8View = new Uint8Array(buffer);  // 8 элементов

int32View[0] = 0x11223344;  // Записали 4 байта

// Другие представления видят те же самые байты
console.log(int16View[0]);   // 0x3344
console.log(int16View[1]);   // 0x1122
console.log(uint8View[0]);   // 0x44
console.log(uint8View[1]);   // 0x33
```

### Концепция view над данными

View — это "очки", через которые мы смотрим на сырые байты. Один и тот же байт может интерпретироваться по-разному в
зависимости от view:

- Через `Uint8Array` — как число 0-255
- Через `Int16Array` — как число со знаком из двух байт
- Через `Float32Array` — как число с плавающей точкой из четырёх байт

```javascript
const buffer = new ArrayBuffer(4);
const int8View = new Int8Array(buffer);
const uint8View = new Uint8Array(buffer);
const int32View = new Int32Array(buffer);
const float32View = new Float32Array(buffer);

int32View[0] = 1065353216;  // В десятичной записи
console.log(float32View[0]); // 1.0 — те же байты интерпретируются как float
```

### API ArrayBuffer

Основные свойства и методы:

- `buffer.byteLength` — размер буфера в байтах
- `buffer.resize(newLength)` — изменение размера (если разрешено)
- `buffer.slice(start, end)` — копирование части буфера
- `buffer.transfer()` — перемещение данных в новый буфер (без копирования, где возможно)

```javascript
const buffer = new ArrayBuffer(16, {maxByteLength: 32});

// Копирование
const copy = buffer.slice(0, 8);
console.log(copy instanceof ArrayBuffer); // true

// Проверка на возможность расширения
if (buffer.resizable) {
    buffer.resize(24);
}
```

## Структуры и хранение сложных данных

Как хранить в типизированных массивах не только числа, но и структуры данных (например, точки, пользователей)?

### Проблема: типизированные массивы хранят только числа

Типизированные массивы не могут напрямую хранить объекты или строки. В них только числа.

```javascript
// Нельзя
const users = new Int32Array(10);
users[0] = {name: "Alice", age: 30};  // Ошибка или преобразование в NaN
```

### Решение: кодирование структур в ArrayBuffer

Можно определяем **схему** — как структура располагается в памяти, а затем пишем/читаем через view.

```javascript
// Структура: точка с координатами x (float32) и y (float32)
// Занимает 8 байт: x (4 байта) + y (4 байта)

// Запись структуры
function writePoint(buffer, offset, x, y) {
    const view = new DataView(buffer);
    view.setFloat32(offset, x, true);      // true = little-endian
    view.setFloat32(offset + 4, y, true);
}

// Чтение структуры
function readPoint(buffer, offset) {
    const view = new DataView(buffer);
    return {
        x: view.getFloat32(offset, true),
        y: view.getFloat32(offset + 4, true)
    };
}

// Использование
const buffer = new ArrayBuffer(16);  // Место для 2 точек
writePoint(buffer, 0, 10.5, 20.3);
writePoint(buffer, 8, 30.1, 40.2);

console.log(readPoint(buffer, 0));  // { x: 10.5, y: 20.3 }
console.log(readPoint(buffer, 8));  // { x: 30.1, y: 40.2 }
```

Чтобы использовать такой подход было удобнее, лучше создать специальную библиотеку или использовать генераторы кода, которые автоматически создают функции сериализации/десериализации по описанию структуры.

Например, FlatBuffers — библиотека от Google, которая реализует view-подход (zero-copy). Данные читаются прямо из буфера без десериализации.

```javascript
// Описание схемы в файле point.fbs
// table Point { x: float; y: float; }

// Сгенерированный код
import { Point } from "./point_generated";

// Создание FlatBuffer
const builder = new flatbuffers.Builder();
const offset = Point.createPoint(builder, 10.5, 20.3);
builder.finish(offset);
const buffer = builder.asUint8Array();

// Чтение (без десериализации — zero-copy!)
const point = Point.getRootAsPoint(buffer);
console.log(point.x()); // 10.5 — мгновенно, без создания объектов
console.log(point.y()); // 20.3
```

### Что выбрать?

| Сценарий                              | Лучший выбор                      | Почему                                          |
|---------------------------------------|-----------------------------------|-------------------------------------------------|
| **Прототипирование, простые данные**  | JS объект                         | Быстро, понятно, нет лишних сложностей          |
| **Высокая нагрузка, real-time, игры** | Бинарное представление через View | Zero-copy чтение, нет GC                        |

## Кортежи

Кортеж (tuple) — это структура, где поля нумеруются (первое, второе, третье), а не именуются как в структуре.

```javascript
// Обычный объект — именованные поля
const namedPoint = {x: 10, y: 20, z: 30};

// Кортеж — нумерованные поля
// В памяти: [байты x][байты y][байты z]
function readTuple(buffer, offset) {
    const view = new DataView(buffer);
    return [
        view.getFloat32(offset, true),
        view.getFloat32(offset + 4, true),
        view.getFloat32(offset + 8, true)
    ];
}
```

## Тегированный указатель

**Тегированный указатель** — техника, когда в самом значении указателя (или числа) часть бит используется для хранения служебной информации. Это позволяет избежать лишних аллокаций и определять тип данных без обращения в кучу.

### Как это используется в JavaScript

JavaScript — язык с динамической типизацией. Движку нужно знать тип каждого значения во время выполнения. Вместо того чтобы выделять объект для каждого числа (что было бы катастрофически медленно и прожорливо), движки используют тегирование прямо в 64-битном значении.

**V8 (движок Chrome/Node.js) использует технику "pointer tagging":**

```javascript
// В JavaScript вы пишете просто:
let a = 42;      // число
let b = "hello"; // строка
let c = true;    // boolean
let d = {};      // объект

// А под капотом V8 хранит 64-битные значения с тегами
```

**Типичная схема тегирования в V8:**

| Тип                                                 | Теговые биты     | Что хранится                          |
|-----------------------------------------------------|------------------|---------------------------------------|
| **Smi (Small Integer)**                             | 0 (младший бит)  | Само число (сдвинутое на 1 бит влево) |
| **HeapObject (объект, строка, массив)**             | 1 (младший бит)  | Указатель на объект в куче            |
| **Special значения (undefined, null, true, false)** | Специальные коды | Предопределённые константы            |

```javascript
// Smi (Small Integer) — хранится прямо в значении
let smi = 42;
// В памяти: (42 << 1) | 0 = 84

// HeapObject — указатель в кучу
let obj = { x: 1 };
// В памяти: указатель на объект в куче, с тегом 1

// Специальные значения — предопределённые константы
let undef = undefined;
let nul = null;
let flag = true;
```

### Почему это важно для JavaScript?

1. Динамическая типизация

   В статически типизированных языках (C, C++, Rust, Java) тип переменной известен на этапе компиляции. Компилятор точно знает, что в `int x` лежит целое число, и генерирует прямой код для работы с ним.

   В JavaScript это не так. Переменная в любой момент может изменить тип:

    ```javascript
    let value = 42;      // сейчас это число
    value = "hello";     // а теперь строка
    value = {};          // а теперь объект
    value = null;        // null
    value = undefined;   // undefined
    ```

   Движку нужно уметь быстро определять тип каждого значения в программе. Тегированные указатели позволяют это делать **без разыменования указателей и обращения к куче**.

2. Гетерогенность коллекций

   Массивы и объекты в JavaScript могут одновременно хранить значения разных типов:

    ```javascript
    const mixedArray = [
        42,           // число
        "hello",      // строка
        true,         // булево
        { x: 1 },     // объект
        null,         // null
        undefined,    // undefined
        42.5          // число с плавающей точкой
    ];
    ```

   В C++ или Rust такой массив пришлось бы реализовывать как массив тегированных объединений (tagged union) или указателей на базовый класс. В JavaScript эта возможность встроена в язык — и тегированные указатели позволяют реализовать её эффективно.

3. **Экономия памяти.** Маленькие числа (Smi) не требуют выделения памяти в куче и не нагружают сборщик мусора. Миллионы чисел могут существовать без единой аллокации.

4. **Скорость.** Определение типа происходит за одну операцию чтения битов, без разыменования указателей.

5. **Компактность.** Одно 64-битное значение содержит и тип, и данные (или указатель).

### Другие примеры использования тегированных указателей

Техника тегирования указателей используется не только в JS-движках:

| Среда                | Применение                                                                                   |
|----------------------|----------------------------------------------------------------------------------------------|
| **Python (CPython)** | Каждый объект — PyObject, но маленькие целые (small ints) кэшируются и используются повторно |
| **Lua**              | Числа хранятся прямо в значении (NaN-тегирование)                                            |
| **Erlang/BEAM**      | Каждое значение тегируется типом                                                             |
| **OCaml**            | Все значения имеют тег в младших битах                                                       |
| **OS/kernel**        | Указатели на память могут тегироваться состоянием (locked, referenced)                       |

### NaN-боксинг (альтернативная техника в JavaScriptCore)

Движок JavaScriptCore (Safari) использует другой подход — **NaN-боксинг (NaN-boxing)**. Он основан на том, что в стандарте IEEE 754 есть много "тихих" NaN-значений с разными полезными нагрузками.

```javascript
// NaN в 64-битном float:
// Биты: [знак:1][показатель:11][мантисса:52]
// NaN: показатель = 2047, мантисса != 0

// JavaScriptCore использует свободные NaN для хранения указателей
// На 64-битной системе:
// - Нормальные float64 — обычные числа с плавающей точкой
// - NaN с ненулевой мантиссой — указатель на объект в куче
```

### Вывод

Тегированные указатели — это не академическая абстракция, а ключевая оптимизация в сердце любого современного интерпретатора или JIT-компилятора динамического языка. Без них JavaScript не мог бы работать с миллионами маленьких чисел без катастрофической нагрузки на GC и память.

Для разработчика понимание этой техники помогает:
- Осознать, почему маленькие целые работают быстрее больших чисел
- Понять, почему все числа в JS — это 64-битные плавающие, но маленькие целые оптимизируются
- Объяснить странное поведение (например, почему `NaN !== NaN`)

## Перечисления (размеченные объединения)

Перечисление (enum) — способ определить тип, который может быть одним из нескольких вариантов. В бинарных данных это часто реализуется через **тег-байт**, который определяет тип следующих данных.

**Проблема:** разные варианты занимают разное количество байт. Нельзя просто сделать массив таких значений, потому что каждый элемент будет иметь разную длину.

### Решения для хранения массива размеченных объединений

Выделяем под каждый элемент максимально возможное количество байт.

```javascript
// Самый большой вариант — прямоугольник (8 байт: 2 float32)
// Круг занимает 4 байта, остальные 4 байта не используются
const SIZE = 8;
const buffer = new ArrayBuffer(100 * SIZE);  // 100 элементов
const view = new DataView(buffer);

function writeCircle(index, radius) {
    const offset = index * SIZE;
    view.setUint8(offset, 1);            // тег
    view.setFloat32(offset + 1, radius, true);
    // байты 5-8 остаются неиспользованными (padding)
}

function writeRect(index, width, height) {
    const offset = index * SIZE;
    view.setUint8(offset, 2);            // тег
    view.setFloat32(offset + 1, width, true);
    view.setFloat32(offset + 5, height, true);
}

function readShape(index) {
    const offset = index * SIZE;
    const type = view.getUint8(offset);

    if (type === 1) {
        return {type: "circle", radius: view.getFloat32(offset + 1, true)};

    } else if (type === 2) {
        return {
            type: "rect",
            width: view.getFloat32(offset + 1, true),
            height: view.getFloat32(offset + 5, true)
        };
    }

    return null;
}
```

### Зачем это нужно? (Разные типы в типизированном массиве)

В обычном JavaScript массиве мы можем хранить любые типы:

```javascript
const jsArray = [42, "hello", true, { x: 1 }, null];
// Это работает, но каждый элемент — это 64-битное слово (тегированный указатель)
// И сами данные (строка, объект) лежат в куче
```

**Ситуации, когда нужно хранить разные типы в типизированном массиве:**

1. **Гетерогенные данные в WebGL/WebGPU** — буферы вершин могут содержать позиции (float32), цвета (uint8), нормали (float32) в одном буфере.

    ```javascript
    // Буфер вершины: позиция (3×float32) + цвет (3×uint8) + нормаль (3×float32)
    // Все данные лежат в одном ArrayBuffer, который уходит в видеокарту
    const vertexBuffer = new ArrayBuffer(100 * (12 + 3 + 12));
    const vertices = new DataView(vertexBuffer);
    // Заполняем...
    gl.bufferData(gl.ARRAY_BUFFER, vertexBuffer, gl.STATIC_DRAW);
    ```

2. **Экономия памяти** — хранить объекты разного размера в одном буфере, чтобы не плодить JS-объекты и не нагружать GC.

3. **Бинарные форматы файлов** — например, в WAV файле чанки (`fmt `, `data`, `INFO`) имеют разные размеры и форматы.

    ```javascript
    // WAV чанк: [type: 4 байта][size: 4 байта][data: size байт]
    // Чанки идут последовательно, их нельзя загнать в плоский типизированный массив
    ```

4. **Сетевые протоколы** — многие бинарные протоколы используют размеченные объединения.

## Выравнивание данных (alignment)

### Что такое выравнивание?

Процессоры эффективнее читают данные, когда они расположены в памяти по адресам, кратным их размеру. Например,
4-байтовое число должно лежать по адресу, кратному 4.

**Правила выравнивания:**

- 1 байт: любой адрес
- 2 байта: адрес кратен 2
- 4 байта: адрес кратен 4
- 8 байт: адрес кратен 8

### Проблема без выравнивания

Если не соблюдать выравнивание, процессору может потребоваться два доступа к памяти вместо одного, что замедляет программу. На некоторых архитектурах это вызывает исключение.

**Но есть и другая проблема: данные могут просто не влезть!**

В типизированных массивах нельзя записать значение, если оно выходит за границы буфера. Но есть более тонкий момент: даже если запись находится в пределах буфера, она может быть невозможна из-за выравнивания.

```javascript
// Плохо: поле int32 лежит по невыровненному адресу
const buffer = new ArrayBuffer(10);
const view = new DataView(buffer);
view.setInt32(1, 42);  // Адрес 1 — не кратен 4!
// Это работает в JS (DataView заботится о совместимости),
// но может быть медленнее

// Хорошо: добавляем padding для выравнивания
// Структура: uint8 (1 байт) + 3 байта padding + int32 (4 байта)
view.setUint8(0, 255);
view.setInt32(4, 42);  // Адрес 4 — кратен 4
```

### Почему данные могут не влезть?

**Проблема с типизированными массивами и невыровненным доступом:**

Типизированные массивы (Int32Array, Float64Array и т.д.) **требуют выравнивания**. Вы не можете создать представление, которое начинается с невыровненного адреса.

```javascript
const buffer = new ArrayBuffer(10);

// Всё хорошо — начинаем с байта 0 (кратен 4)
const int32_ok = new Int32Array(buffer, 0, 2);

// Ошибка! Байт 1 не кратен 4 для 32-битных целых
const int32_bad = new Int32Array(buffer, 1, 2);
// RangeError: start offset of Int32Array should be a multiple of 4
```

**То же самое для других типов:**

| Тип массива                                 | Требование к выравниванию |
|---------------------------------------------|---------------------------|
| Int8Array, Uint8Array                       | Любой адрес (1 байт)      |
| Int16Array, Uint16Array, Float16Array       | Адрес кратен 2            |
| Int32Array, Uint32Array, Float32Array       | Адрес кратен 4            |
| Float64Array, BigInt64Array, BigUint64Array | Адрес кратен 8            |

```javascript
const buffer = new ArrayBuffer(20);

// Int16Array — нужен адрес кратен 2
const int16_ok = new Int16Array(buffer, 2, 4);   // ok: 2 кратен 2
const int16_bad = new Int16Array(buffer, 1, 4);  // ошибка: 1 не кратен 2

// Float64Array — нужен адрес кратен 8
const float64_ok = new Float64Array(buffer, 8, 1);  // ok: 8 кратен 8
const float64_bad = new Float64Array(buffer, 4, 1); // ошибка: 4 не кратен 8
```

### Как обойти эту проблему?

**Вариант 1: Использовать DataView**

DataView не требует выравнивания и позволяет читать/писать с любого адреса.

```javascript
const buffer = new ArrayBuffer(20);
const view = new DataView(buffer);

// DataView не требует выравнивания
view.setInt16(1, 1000);      // ok, хотя адрес 1
view.setInt32(2, 50000);     // ok, хотя адрес 2
view.setFloat64(3, 3.14159); // ok, хотя адрес 3

// Всё работает, но может быть медленнее
```

**Вариант 2: Добавить padding (выравнивание)**

Проектируем структуру так, чтобы все поля начинались с правильных адресов.

```javascript
// Структура: uint8 + uint32 + uint16
// Правильно: [uint8][3 байта padding][uint32][uint16][2 байта padding]
const buffer = new ArrayBuffer(1 + 3 + 4 + 2 + 2);
const uint8View = new Uint8Array(buffer);
const uint32View = new Uint32Array(buffer, 4, 1);  // сдвиг 4, кратен 4
const uint16View = new Uint16Array(buffer, 8, 1);  // сдвиг 8, кратен 2

uint8View[0] = 255;
uint32View[0] = 123456789;
uint16View[0] = 32000;
```

### Когда это важно на практике?

**1. Парсинг бинарных протоколов**

Сетевые протоколы часто упаковывают данные без учета выравнивания, экономя каждый байт.

```javascript
// Пример: заголовок пакета (без выравнивания)
// [type:1][id:2][length:4][flags:1] = 8 байт
// Поля id (2 байта) начинается с адреса 1 — не кратен 2!
// Поле length (4 байта) начинается с адреса 3 — не кратен 4!

function parsePacket(buffer) {
    const view = new DataView(buffer);
    return {
        type: view.getUint8(0),
        id: view.getUint16(1, true),   // адрес 1 — ok для DataView
        length: view.getUint32(3, true), // адрес 3 — ok для DataView
        flags: view.getUint8(7)
    };
}
```

**2. Чтение файловых форматов (BMP, WAV, ZIP)**

Многие форматы файлов не используют выравнивание, чтобы не раздувать размер.

**3. Экономия памяти**

Выравнивание добавляет padding (пустые байты). При передаче данных по сети или хранении на диске каждый байт на счету.

```javascript
// Без выравнивания: 1 + 2 + 4 + 1 = 8 байт
// С выравниванием: 1 + 3 + 4 + 2 = 10 байт (на 25% больше!)
```

## DataView — универсальный инструмент для чтения/записи

### API DataView

`DataView` — это view, который позволяет читать и записывать различные типы данных в любом месте `ArrayBuffer` с
контролем порядка байт.

```javascript
const buffer = new ArrayBuffer(16);
const view = new DataView(buffer);

// Запись разных типов
view.setInt8(0, 127);           // 1 байт
view.setUint16(1, 65535, true); // 2 байта, little-endian
view.setFloat32(3, 3.14159, true); // 4 байта
view.setFloat64(7, 2.71828, true); // 8 байт

// Чтение
console.log(view.getInt8(0));     // 127
console.log(view.getUint16(1, true)); // 65535
console.log(view.getFloat32(3, true)); // 3.14159
console.log(view.getFloat64(7, true)); // 2.71828
```

### Проблема с endianness (порядком байт)

**Endianness** — это порядок, в котором байты числа записываются в памяти. Это **особенность конкретного процессора и архитектуры**, а не программного обеспечения. Разные архитектуры используют разный порядок байт:

- **Little-endian:** младший байт первым (x86, x86-64, ARM, ARM64, RISC-V)
- **Big-endian:** старший байт первым (PowerPC, SPARC, Motorola 68k, сетевые протоколы)

### Как endianness влияет на разные API в JavaScript

**Типизированные массивы (Uint32Array, Int16Array и т.д.)** — всегда используют **нативный порядок байт** процессора. Это сделано для максимальной производительности, так как данные читаются напрямую без перестановок.

```javascript
const buffer = new ArrayBuffer(4);
const uint32 = new Uint32Array(buffer);
uint32[0] = 0x11223344;

// Порядок байт в памяти зависит от процессора:
// На x86/ARM (little-endian): [0x44, 0x33, 0x22, 0x11]
// На PowerPC (big-endian):   [0x11, 0x22, 0x33, 0x44]
```

**DataView** — более гибкий. Он не использует нативный порядок автоматически. Вместо этого:

- **По умолчанию** — big-endian (если не указан флаг)
- **С флагом `true`** — little-endian

```javascript
const buffer = new ArrayBuffer(4);
const view = new DataView(buffer);
const value = 0x11223344;

// Явно указываем little-endian (флаг true)
view.setUint32(0, value, true);
console.log([...new Uint8Array(buffer)]);
// ВСЕГДА: [0x44, 0x33, 0x22, 0x11] (независимо от процессора)

// Явно указываем big-endian (флаг false)
view.setUint32(0, value, false);
console.log([...new Uint8Array(buffer)]);
// ВСЕГДА: [0x11, 0x22, 0x33, 0x44] (независимо от процессора)
```

### В чём проблема? (Передача данных между разными системами)

Проблема возникает, когда данные, записанные на одном компьютере, передаются на другой компьютер с другой архитектурой.

**Сценарий проблемы:**

1. Сервер на **ARM (little-endian)** записывает число `0x11223344` в файл или буфер через `Uint32Array`
2. В памяти оказалось: `[0x44, 0x33, 0x22, 0x11]`
3. Файл отправляется на компьютер с **PowerPC (big-endian)**
4. Компьютер читает файл через `Uint32Array`
5. Он интерпретирует те же байты как `0x44332211` — **совсем другое число!**

```javascript
// НА СЕРВЕРЕ (little-endian: x86/ARM)
const serverBuffer = new ArrayBuffer(4);
const serverArray = new Uint32Array(serverBuffer);
serverArray[0] = 0x11223344;
// В памяти: [0x44, 0x33, 0x22, 0x11]

// Отправляем serverBuffer клиенту...

// НА КЛИЕНТЕ (big-endian: PowerPC)
const clientBuffer = получаем_буфер_от_сервера(); // [0x44, 0x33, 0x22, 0x11]
const clientArray = new Uint32Array(clientBuffer);
console.log(clientArray[0].toString(16)); // "44332211" — УПС! Неправильное число
```

### Решение: согласование endianness

Чтобы данные правильно интерпретировались на любой системе, нужно договориться о едином порядке байт при передаче.

**Стандарт:** сетевые протоколы (TCP/IP, HTTP) и многие бинарные форматы используют **big-endian** (так называемый "сетевой порядок байт").

**Практика:** всегда использовать **DataView** с явным указанием порядка байт при передаче данных между системами.

```javascript
// ПРАВИЛЬНО: при записи данных для передачи
function writeForNetwork(buffer, offset, value) {
    const view = new DataView(buffer);
    view.setUint32(offset, value, false); // false = big-endian (сетевой порядок)
}

// ПРАВИЛЬНО: при чтении данных из сети
function readFromNetwork(buffer, offset) {
    const view = new DataView(buffer);
    return view.getUint32(offset, false); // false = big-endian
}

// Пример: запись числа на сервере (любая архитектура)
const buffer = new ArrayBuffer(4);
writeForNetwork(buffer, 0, 0x11223344);
// В памяти теперь ВСЕГДА: [0x11, 0x22, 0x33, 0x44]

// Клиент (любая архитектура) прочитает правильно
const value = readFromNetwork(buffer, 0);
console.log(value.toString(16)); // "11223344" — ПРАВИЛЬНО!
```

### Как определить нативный endian системы (little-endian или big-endian)

В JavaScript нет прямого способа узнать, с каким порядком байт работает процессор. Однако это можно определить через небольшой хак с использованием типизированных массивов.

```javascript
function isLittleEndian() {
    // Создаём 32-битный массив с одним элементом
    const header = new Uint32Array(1);

    // Создаём DataView поверх того же буфера
    const view = new DataView(header.buffer);

    // Записываем число, у которого каждый байт разный
    // 0x01 0x23 0x45 0x67 (в старший→младший порядок)
    header[0] = 0x01234567;
    
    // Читаем 32-битное число через DataView с явным little-endian
    // Если нативный порядок little-endian, числа совпадут
    // Если нативный big-endian, числа будут разными
    return header[0] === view.getUint32(0, true);
}

console.log(isLittleEndian()); // true на x86, ARM; false на некоторых старых архитектурах
```

#### Как это работает?

1. `Uint32Array` хранит число в **нативном для системы** порядке байт.
2. Записываем число `0x01234567`, где байты идут в явном порядке: `01 23 45 67`.
3. `DataView.getUint32(0, true)` принудительно читает эти байты как **little-endian** (младший байт первым).
4. Если нативная система тоже little-endian — числа совпадут. Если big-endian — прочитается перевёрнутое значение.

## Парсинг данных при использовании view подхода

View-подход означает, что мы не копируем данные, а читаем их прямо из буфера "на лету". Это называется **zero-copy
парсинг**.

```javascript
// Классический подход: парсинг в объекты (копирование)
function parseUserObject(buffer) {
    const view = new DataView(buffer);
    return {
        id: view.getUint32(0, true),      // Копируем значение
        age: view.getUint16(4, true),
        score: view.getFloat32(6, true)
    };
}

// Создаётся объект, данные копируются из буфера

// View-подход: чтение по требованию
class UserView {
    constructor(buffer) {
        this.view = new DataView(buffer);
    }

    get id() {
        return this.view.getUint32(0, true);
    }

    get age() {
        return this.view.getUint16(4, true);
    }

    get score() {
        return this.view.getFloat32(6, true);
    }
}

// Данные не копируются, читаются только когда запрошены
```

Преимущества view-подхода:

- Нет лишних аллокаций памяти под объекты
- Меньше работы сборщика мусора
- Мгновенный доступ к данным (не нужно ждать парсинга)

Недостатки:

- API менее удобный (геттеры вместо прямых свойств)
- Каждый доступ выполняет чтение из буфера (не кэшируется)

## Методы типизированных массивов

### subarray vs slice

**subarray** — создаёт новый view на ту же память (не копирует данные).
**slice** — создаёт новый view и копирует данные.

```javascript
const original = new Uint8Array([1, 2, 3, 4, 5]);

// subarray — без копирования
const sub = original.subarray(1, 4);  // [2, 3, 4]
sub[0] = 99;
console.log(original);  // [1, 99, 3, 4, 5] — оригинал изменился!

// slice — с копированием
const sliced = original.slice(1, 4);  // [99, 3, 4]
sliced[0] = 42;
console.log(original);  // [1, 99, 3, 4, 5] — оригинал не изменился
```

### Метод set

`set` позволяет копировать данные из другого массива (обычного или типизированного) в текущий.

```javascript
const target = new Int32Array(10);
const source = [1, 2, 3, 4, 5];

// Копируем source в target начиная с индекса 2
target.set(source, 2);
console.log(target);  // [0, 0, 1, 2, 3, 4, 5, 0, 0, 0]
```

### Новое в ES2025: toBase64, toHex, fromBase64, fromHex

Новые методы для работы с бинарными данными:

```javascript
// ДО ES2025 — нужно писать вручную или использовать библиотеки
const uint8 = new Uint8Array([72, 101, 108, 108, 111]);
const base64 = btoa(String.fromCharCode(...uint8));  // "SGVsbG8="

// ПОСЛЕ ES2025 — встроенные методы
const newUint8 = new Uint8Array([72, 101, 108, 108, 111]);
const base64 = newUint8.toBase64();  // "SGVsbG8="
const hex = newUint8.toHex();        // "48656c6c6f"

// Обратное преобразование
const fromBase64 = Uint8Array.fromBase64("SGVsbG8=");  // [72,101,108,108,111]
const fromHex = Uint8Array.fromHex("48656c6c6f");      // [72,101,108,108,111]
```

## Итоги лекции

### Ключевые выводы

1. **Типизированные массивы** — это эффективный способ работы с бинарными данными в JavaScript. Они экономят память и
   работают быстрее обычных массивов для числовых данных.

2. **ArrayBuffer** — сырая область памяти (набор байт). Сам по себе не имеет способов чтения/записи.

3. **Виды представлений:**
  - **Типизированные массивы (Int32Array и т.д.)** — для работы с однородными массивами чисел.
  - **DataView** — для чтения/записи произвольных типов в произвольных местах буфера с контролем endianness.

4. **Один ArrayBuffer может иметь множество представлений**, которые интерпретируют одни и те же байты по-разному.

5. **Для хранения сложных структур** в типизированных массивах нужно кодировать их вручную, рассчитывая смещения и
   учитывая выравнивание.

6. **Endianness важен** при передаче данных между разными системами. DataView даёт полный контроль.

7. **View-подход (zero-copy парсинг)** позволяет читать данные из буфера без копирования и десериализации, что экономит
   память и ускоряет доступ.

### Когда использовать

**Типизированные массивы подходят для:**

- Численных расчётов и обработки больших массивов чисел
- Работы с файлами, изображениями, аудио, видео
- Сетевых протоколов (WebSocket, WebRTC, gRPC)
- WebGL и графики
- Реализации собственных бинарных форматов и структур

**Обычные массивы лучше оставить для:**

- Повседневной работы с данными, где нужна гибкость
- Хранения разнородных данных
- Простоты и читаемости кода
- Когда размер данных не критичен
