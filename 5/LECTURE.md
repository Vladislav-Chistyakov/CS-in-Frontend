# AI конспект для лекции #5

## Бенчмарк: две функции для обхода массива (по строкам и по столбцам)

Классический пример, демонстрирующий важность порядка доступа к памяти. Представим двумерный массив (матрицу) размером
10000×10000.

**Обход по строкам (row-major):**

```js
function rowMajor(array, size) {
	let sum = 0;
	for (let i = 0; i < size; i++) {
		for (let j = 0; j < size; j++) {
			const index = i * size + j;
			sum += array[index];
		}
	}
	return sum;
}
```

**Обход по столбцам (column-major):**

```js
function columnMajor(array, size) {
	let sum = 0;
	for (let i = 0; i < size; i++) {
		for (let j = 0; j < size; j++) {
			const index = j * size + i;
			sum += array[index];
		}
	}
	return sum;
}
```

Результаты бенчмарка: Функция rowMajor стабильно быстрее в 1.5-2 раза на числовом массиве, а с массивом объектов уже быстрее в 3-5 раза! Чем больше массив – тем разница больше.

## Порядок обхода важен, а не направление

Важно не то, в какую сторону (вперёд или назад) мы идём по массиву, а то, **насколько последовательно** мы обращаемся к
соседним ячейкам памяти.

- Последовательный доступ (идём подряд по адресам) — быстрый
- Произвольный доступ (прыгаем по памяти) — медленный

Двумерный массив в памяти хранится **построчно** (row-major order):

```text
Физическое расположение в памяти:
[строка0[0], строка0[1], строка0[2], ..., строка1[0], строка1[1], ...]

Обход по строкам:   ✅ последовательный (соседние адреса)
Обход по столбцам:  ❌ прыгает через всю строку (шаг = N элементов)
```

## Доступ к элементу массива по индексу и оперативная память

Когда мы пишем `arr[i]`, происходит обращение к оперативной памяти (RAM) по адресу `базовый_адрес + i * размер_элемента`.
Чтение DRAM памяти по заданному адресу условно константная операция.

## Размер указателя или ссылки

**Указатель** — это число, хранящее адрес в памяти. Его размер зависит от архитектуры:

| Архитектура | Размер указателя | Максимальная адресуемая память |
|-------------|------------------|--------------------------------|
| 16-битная   | 2 байта          | 64 КБ                          |
| 32-битная   | 4 байта          | 4 ГБ                           |
| 64-битная   | 8 байт           | 16 ЭБ (эксабайт)               |

В 64-битной системе указатель занимает 8 байт. Но это создаёт проблему: если хранить много указателей, они потребляют
много памяти и забивают кэш.

## Оптимизация V8: сжатые указатели (32 бита даже на 64-битной системе)

V8 (JavaScript-движок Chrome/Node.js) использует хитрый трюк: **сжатые указатели**.

**Идея:** большинству объектов в JavaScript не нужны все 64 бита адреса. Достаточно 32 бит (4 ГБ адресного
пространства), если разместить все объекты в одном непрерывном блоке памяти.

**Как работает:**

1. V8 резервирует большой непрерывный блок памяти (обычно 4 ГБ)
2. Все объекты создаются внутри этого блока
3. Вместо полного 64-битного адреса хранится 32-битное **смещение** внутри блока
4. При обращении смещение складывается с базовым адресом блока

**Результат:**

- Экономия памяти (указатели занимают в 2 раза меньше места)
- Больше объектов помещается в кэш
- Производительность выше

## Процессор и память

Процессор — это вычислительное ядро. Память — это место, где лежат данные. Проблема: процессор работает намного быстрее,
чем память.

**Важно:** процессор может выполнить десятки инструкций, пока ждёт одно чтение из RAM. Поэтому оптимизация работы с
памятью критически важна.

### Память с точки зрения процессора

Для процессора память — это просто большой массив байт. У каждого байта есть свой адрес. Процессор может:

- Прочитать байт по адресу
- Записать байт по адресу
- Прочитать/записать несколько байт за раз (слово: 2, 4, 8 байт)

Но процессор не работает напрямую с RAM. Между ними находится **кэш**.

### Регистры процессора

**Регистры** — это сверхбыстрая память внутри процессора. Их очень мало (обычно 16-32), но доступ к ним занимает 1 такт.

**Типы регистров:**

- **Общего назначения** — для хранения промежуточных значений (RAX, RBX, RCX, RDX на x86)
- **Счётчик команд (PC/RIP)** — хранит адрес текущей инструкции
- **Указатель стека (RSP)** — хранит вершину стека
- **Флаги** — хранят результат сравнения (ноль, перенос, переполнение)

```js
// На JavaScript мы не работаем с регистрами напрямую
// Но под капотом код компилируется в инструкции, которые используют регистры
let a = 5;     // Значение 5 может оказаться в регистре RAX
let b = 10;    // Значение 10 в регистре RBX
let c = a + b; // Инструкция ADD RAX, RBX
```

**Важно для понимания:** переменные, которые активно используются, могут жить в регистрах и не занимать место в памяти
или кэше.

### Кэш-память

**Кэш** — это небольшой, но быстрый буфер между процессором и памятью. В современных процессорах x86 используется 3 уровня
кэша:

**L1 (Level 1)** — самый быстрый, самый маленький (обычно 32-48 КБ на ядро)

- Разделён на L1I (инструкции) и L1D (данные)

**L2 (Level 2)** — больше, медленнее (256 КБ - 1 МБ на ядро)

**L3 (Level 3)** — самый большой, самый медленный (8-32 МБ, общий для всех ядер)

**Как работает кэш:**

1. Процессор хочет прочитать данные по адресу
2. Сначала проверяет L1 — есть? → попадание (hit)
3. Нет? → проверяет L2
4. Нет? → проверяет L3
5. Нет? → промах (miss) → читает из RAM
6. Прочитанные данные сохраняются во всех уровнях кэша

#### Кэш-линии

Кэш работает не с отдельными байтами, а с блоками фиксированного размера — **кэш-линиями**. Типичный размер кэш-линии для x86: *
*64 байта**.

**Что это значит:**

- Когда процессор читает 1 байт из памяти, он на самом деле читает 64 байта (целую кэш-линию)
- Соседние байты подтягиваются "бесплатно"

```text
Если мы читаем элемент массива по индексу i, в кэш подтягиваются элементы i, i+1, i+2, ... i+15 (для 4-байтных элементов)

Обход по строкам:     каждый раз читаем следующий элемент из той же кэш-линии ✅
Обход по столбцам:    каждый раз прыгаем на N элементов, попадаем в новую кэш-линию ❌
```

##### Влияет ли размер элемента на количество элементов в кэш-линии?

Да! Кэш-линия фиксированного размера (64 байта) помещает:

- 64 элемента типа `Uint8Array` (1 байт)
- 32 элемента `Uint16Array` (2 байта)
- 16 элементов `Uint32Array` или `Float32Array` (4 байта)
- 8 элементов `Float64Array` или `BigUint64Array` (8 байт)

Поэтому работа с маленькими типами данных эффективнее с точки зрения кэша.

## Как хранятся значения JS в памяти

JavaScript-значения из-за динамической типизации хранятся в виде указателей, однако некоторые значения по факту указателями не являются и хранят свои данные в самом указателе, например, SMI (Small Integer).

**Важно для понимания кэша:** массив в JavaScript — это массив **указателей**. Сами значения могут быть разбросаны по памяти.

### Массив ссылок — проблема для кэша

```js
// Обычный массив JavaScript
const arr = [obj1, obj2, obj3, obj4];
```

В памяти:

- Сам массив: непрерывный блок указателей (4/8 байт каждый)
- Объекты: разбросаны по куче

**Проблема:** когда мы обходим массив и обращаемся к полям объектов, процессор прыгает туда-сюда между массивом и кучей.
Кэш-промахи обеспечены.

### Типизированные массивы и кэш

**Типизированные массивы** (TypedArray) решают эту проблему: они хранят сами данные, а не указатели.

```js
// Типизированный массив — данные лежат непрерывно
const arr = new Float64Array(1_000_000);

for (let i = 0; i < arr.length; i++) {
	arr[i] = Math.sin(i);
}
```

В памяти: `[значение0, значение1, значение2, ...]` — непрерывно, без указателей.

**Результат:** отличная локальность данных, эффективное использование кэша, скорость работы близка к C/C++.

## Многоуровневая архитектура кэша

Современный процессор Intel или AMD:

```text
┌─────────────────────────────────────────────────────────────┐
│                         Ядро 0                              │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐                   │
│  │  L1I     │  │  L1D     │  │  L2      │                   │
│  │  32 КБ   │  │  48 КБ   │  │  1 МБ    │                   │
│  └──────────┘  └──────────┘  └──────────┘                   │
└─────────────────────────────────────────────────────────────┘
↓
┌─────────────────────────────────────────────────────────────┐
│                    L3 (общий на все ядра)                   │
│                        16-32 МБ                             │
└─────────────────────────────────────────────────────────────┘
↓
┌─────────────────────────────────────────────────────────────┐
│                       RAM (оперативная память)              │
│                        16-128 ГБ                            │
└─────────────────────────────────────────────────────────────┘
```

**Почему несколько уровней?** Компромисс между скоростью и размером. L1 очень быстрый, но маленький. L3 большой, но
медленнее. При промахе в L1 проверяется L2, потом L3.

## Пирамида скорости памяти

Иерархия памяти от самой быстрой до самой медленной:

```text
Регистры (1 такт)           → очень мало (сотни байт)
L1 кэш (2-4 такта)          → 32-48 КБ
L2 кэш (10-20 тактов)       → 256 КБ - 1 МБ
L3 кэш (30-50 тактов)       → 8-32 МБ
RAM (100-300 тактов)        → 16-128 ГБ
SSD (миллионы тактов)       → 512 ГБ - 4 ТБ
HDD (десятки миллионов)     → 1-20 ТБ
Сеть (сотни миллионов)      → бесконечно (облако)
```

**Золотое правило:** чем реже уровень используется, тем больше данных на нём помещается, но тем дольше доступ.

## Другие оптимизации

Помимо кэша, современные процессоры используют множество техник для ускорения работы:

1. **Предсказание ветвлений (branch prediction)** — угадывание, какая ветка `if` будет выполнена
2. **Спекулятивное выполнение** — выполнение инструкций заранее, до проверки условия
3. **Векторизация (SIMD)** — выполнение одной операции над множеством данных
4. **Конвейеризация** — одновременное выполнение нескольких инструкций на разных этапах

### Предсказание ветвлений (branch prediction)

**Проблема:** когда процессор встречает условие `if (x > 0)`, он не знает, какую ветку выполнять, пока не вычислит
`x > 0`. Но ждать нельзя — это простои.

**Решение:** предсказатель ветвлений угадывает, какая ветка будет выполнена, и начинает выполнять её спекулятивно.

```js
// Легко предсказать (всегда true на первой итерации?)
for (let i = 0; i < 1000000; i++) {
	if (i < 500000) { // Предсказатель быстро учится
	// Одна ветка
	} else {
	// Другая ветка
	}
}

// Трудно предсказать (случайно)
for (let i = 0; i < 1000000; i++) {
	if (Math.random() > 0.5) { // Случайно!
	// предсказатель ошибается в ~50% случаев
	}
}
```

**Точность современных предсказателей:** >95% для предсказуемых паттернов. Но случайные данные убивают
производительность.

### Прогрев памяти и спекулятивное выполнение

**Прогрев памяти (memory warming)** — предварительная загрузка данных в кэш до того, как они понадобятся.

**Спекулятивное выполнение** — процессор начинает выполнять инструкции, даже не зная точно, нужны ли они (например,
после `if`). Если предсказание оказалось неверным, результаты отбрасываются.

Это работает, но породило уязвимости...

### Уязвимости Meltdown и Spectre (2018)

**Meltdown:** спекулятивное выполнение может получить доступ к защищённой памяти ядра, а потом откатить изменения. Но
следы в кэше остаются, позволяя прочитать данные.

**Spectre:** аналогично, но использует предсказание ветвлений для чтения данных из других процессов.

**Последствия:**

- Все современные процессоры (Intel, AMD, ARM) уязвимы
- Патчи в ОС снижают производительность на 5-30%
- JavaScript-код в браузере теоретически может эксплуатировать Spectre

**Защита в браузерах:**

- Уменьшение точности таймеров (performance.now)
- Изоляция сайтов (Site Isolation в Chrome)
- Отключение SharedArrayBuffer (частично вернули с ограничениями)

### Оптимизации компилятора/JIT: векторизация

**Векторизация** — это преобразование циклов, при котором компилятор заменяет последовательные операции на
SIMD-инструкции.

**Пример без векторизации:**

```js
for (let i = 0; i < 1024; i++) {
	c[i] = a[i] + b[i];
}
```

Компилятор может сгенерировать код, который складывает не по одному элементу, а по 4 или 8 одновременно.

#### SIMD-инструкции

**SIMD (Single Instruction, Multiple Data)** — инструкции, которые выполняют одну операцию над несколькими элементами
данных одновременно.

**Примеры SIMD-расширений процессоров:**

- **MMX** (1997) — 64-битные
- **SSE** (1999) — 128-битные
- **AVX** (2011) — 256-битные
- **AVX-512** (2016) — 512-битные

**Что это даёт:** одна AVX-512 инструкция может сложить 16 чисел с плавающей точкой (32-битных) за один такт.

```text
Обычное сложение:                SIMD сложение:
a[0]+b[0] → c[0]                [a0 a1 a2 a3] + [b0 b1 b2 b3] → [c0 c1 c2 c3]
a[1]+b[1] → c[1]                1 инструкция, 4 операции
a[2]+b[2] → c[2]                Ускорение до 4 раз
a[3]+b[3] → c[3]
4 инструкции
```

##### WebAssembly и SIMD

WebAssembly (WASM) поддерживает SIMD-инструкции с 2018 года. Это позволяет компилировать C++/Rust-код с векторизацией в
WASM, получая огромный прирост производительности в браузере.

**Области применения:**

- Обработка изображений (фильтры, распознавание)
- Аудио и видео кодеки
- 3D-графика (WebGL)
- Математические вычисления (научные расчёты, машинное обучение)

## Итоги лекции

1. **Порядок обхода данных критичен.** Последовательный доступ (по строкам) использует кэш-линии эффективно и может быть
   в разы быстрее произвольного.

2. **Иерархия памяти:** регистры → L1 → L2 → L3 → RAM → диск. Каждый следующий уровень больше, но медленнее.

3. **Кэш-линии (64 байта)** — процессор всегда читает блоки целиком. Используйте это: обходите данные последовательно,
   группируйте связанные поля.

4. **Типизированные массивы** (TypedArray) хранят данные непрерывно и эффективно используют кэш. В отличие от обычных
   массивов, которые зачастую хранят указатели.

5. **Предсказание ветвлений** ускоряет предсказуемый код и замедляет случайный. Пишите предсказуемые условия.

6. **SIMD** (векторизация) позволяет выполнять одну операцию над множеством данных. Доступна в WebAssembly.

7. **Уязвимости Meltdown/Spectre** — побочный эффект спекулятивного выполнения. Привели к изменениям в браузерах и ОС.
