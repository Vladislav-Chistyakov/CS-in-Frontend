# AI конспект для лекции #10

## Абстрактные структуры данных

### Что это такое?

Абстрактные структуры данных (АСД) описывают **контракт** — что должна делать структура (какие методы, что возвращают),
но не говорят, **как именно** это реализовать.

**Пример из JavaScript:** спецификация не говорит, что массив — это вектор или хеш-таблица. Она описывает какие методы
должны быть и какие инварианты соблюдаться. Как именно движок это реализует — его дело.

**Смысл абстрактности:**

- Выделение главных контрактов
- Возможность легко менять реализацию под требования
- Оптимизация под конкретный сценарий без изменения кода, использующего АСД

## Стек и очередь

### Стек (Stack)

**Инвариант:** LIFO (Last In, First Out) — последним зашёл, первым вышел.

**Операции:**

- `push(item)` — добавить элемент в конец последовательности
- `pop()` — прочитать и удалить последний элемент
- `peek()` (часто) — посмотреть последний элемент без удаления

**Визуализация:** стопка книг. Кладу сверху — беру сверху. До нижней не добраться, пока не сниму все верхние.

### Очередь (Queue)

**Инвариант:** FIFO (First In, First Out) — первым пришёл, первым ушёл.

**Операции:**

- `enqueue` / `push` — добавить элемент в конец
- `dequeue` / `shift` — прочитать и удалить первый элемент

**Визуализация:** очередь в магазине. Новый человек встаёт в конец, обслуживают первого.

### Зачем нужны стек и очередь?

- Парсинг и конечные автоматы
- Реализация вызовов функций (call stack)
- Обработка запросов в асинхронных системах
- Алгоритмы на графах (BFS — очередь, DFS — стек)
- Управление историей (undo/redo — два стека)

## Двусторонняя очередь (Deque, Double-Ended Queue)

Deque (произносится "дек", от Double-Ended QUEue) — очередь, которая умеет добавлять и удалять элементы с **обоих концов
**.

**Операции:**

- `pushBack` / `pushFront` — добавление в конец / начало
- `popBack` / `popFront` — удаление с конца / начала

## Массив как реализация стека, очереди и дека

В JavaScript обычный массив уже предоставляет методы для всех трёх АСД:

| АСД         | Необходимые операции         | Встроенные методы JS                      |
|-------------|------------------------------|-------------------------------------------|
| **Стек**    | push / pop                   | `push()`, `pop()`                         |
| **Очередь** | push / shift                 | `push()`, `shift()`                       |
| **Дек**     | push / pop / unshift / shift | `push()`, `pop()`, `unshift()`, `shift()` |

## Проблема очереди на массиве

При использовании `shift()` на обычном массиве возникает проблема: удаление первого элемента требует **сдвига всех
остальных элементов влево**. Это операция O(n).

**Почему сдвиг нужен?** Контракт массива требует, чтобы элементы лежали непрерывно без дырок с нулевого индекса. При
удалении первого элемента образуется дырка, её нужно заполнить сдвигом.

## Решение 1: Вставка в середину массива с двумя указателями

Идея: вместо того чтобы хранить элементы с начала массива, храним их **где-то в середине** выделенного буфера, а границы
отмечаем указателями `start` и `end`.

**Как работает:**

- При создании буфера start и end указывают на середину
- `unshift` (добавление в начало) — сдвигаем start влево, записываем элемент
- `push` (добавление в конец) — записываем по end, сдвигаем end вправо
- `shift` (удаление из начала) — читаем по start, сдвигаем start вправо
- `pop` (удаление из конца) — сдвигаем end влево, читаем

**Плюсы:**

- Нет сдвига элементов
- Хорошая локальность данных

**Минусы:**

- При добавлении только в один конец расходуется только половина памяти

## Решение 2: Кольцевой буфер (Ring Buffer / Circular Buffer)

Развитие предыдущего решения. Указатели двигаются не просто влево/вправо, а **по кругу**. При достижении левого края
перескакивают на правый, и наоборот.

**Как зациклить индекс:**

```text
newIndex = (currentIndex + 1) % capacity
newIndex = (currentIndex - 1 + capacity) % capacity
```

**Плюсы:**

- Полное использование памяти
- Нет сдвигов

**Минусы:**

- Локальность данных чуть хуже (элементы могут быть разбросаны по буферу)
- Сложная математика

## Фиксированный размер очереди без аллокаций

Если максимальный размер очереди известен заранее, не обязательно делать динамическое расширение. Возможные стратегии:

1. **Отказ при переполнении** — клиент получает ошибку, не может добавить элемент
2. **Перезапись старых данных** — при добавлении в заполненную очередь перезаписываются самые старые элементы

Фиксированные кольцевые буферы широко используются во **встраиваемых системах** и **real-time приложениях**, где
динамическая память недоступна.

## Можно ли избавиться от копирования при расширении?

### Проблема расширения массива

Когда в векторе заканчивается ёмкость, приходится:

1. Выделять новый массив большей ёмкости
2. Копировать все элементы
3. Освобождать старый

Это дорогая операция O(n).

### Решение: отказ от непрерывной памяти

Если отказаться от требования непрерывности памяти, то расширение становится дешёвым — просто выделяем новый блок где-то
в другом месте и связываем ссылкой.

## Связный список (Linked List)

### Что это?

Связный список — структура, в которой каждый элемент (узел) содержит:

- **Значение** (value)
- **Указатель на следующий элемент** (next)

Последний элемент указывает на `null`.

### Простейшая реализация на JavaScript

```javascript
const node3 = { value: 30, next: null };
const node2 = { value: 20, next: node3 };
const node1 = { value: 10, next: node2 };

let head = node1;

// Обход списка
let current = head;
while (current !== null) {
    console.log(current.value);
    current = current.next;
}
```

### Свойства связного списка

| Операция                                   | Сложность |
|--------------------------------------------|-----------|
| Добавление в начало                        | O(1)      |
| Удаление из начала                         | O(1)      |
| Добавление в конец (без указателя на tail) | O(n)      |
| Добавление в конец (с tail)                | O(1)      |
| Доступ по индексу                          | O(n)      |
| Поиск элемента                             | O(n)      |

## 12. Реализация стека на связанном списке

В стеке элементы добавляются и удаляются с одного конца. В связном списке проще всего реализовать это через начало
списка.

```javascript
class Stack {
    constructor() {
        this.head = null;
    }

    push(value) {
        this.head = {value, next: this.head};
    }

    pop() {
        if (!this.head) return undefined;
        const value = this.head.value;
        this.head = this.head.next;
        return value;
    }

    peek() {
        return this.head?.value;
    }
}
```

**Преимущество:** нет проблем с расширением — каждый новый элемент просто создаётся в куче.

## Реализация очереди на связанном списке

Для очереди нужно добавлять в конец, а удалять из начала. Поэтому потребуется:

- **head** — указатель на начало (откуда удаляем)
- **tail** — указатель на конец (куда добавляем)
- Двусвязный список (со ссылкой не только на next, но и на prev) для удобства

Двусвязный список (Doubly Linked List):

- Каждый узел имеет `prev` и `next`
- Позволяет эффективно удалять последний элемент (не нужно искать предыдущий обходом)

**Операции:**

- `push` (добавление в конец) — O(1)
- `shift` (удаление из начала) — O(1)

## Бенчмарк: массив vs связный список

**Результаты (на примере обхода и суммирования элементов):**

- Массив: 1x (базовый)
- Связный список: в 2 раза медленнее

**Причина — локальность данных:**

- В массиве элементы лежат рядом и попадают в кэш-линии
- В связном списке узлы разбросаны по памяти, каждый следующий — это промах кэша

## Вопрос: массив объектов — это то же самое?

Нет, не то же самое. В массиве объектов хранятся **указатели** на сами объекты. Указатели лежат рядом в массиве и хорошо
попадают в кэш. В связном списке нужно сначала прочитать указатель на следующий узел, а затем пойти по нему — два
промаха кэша.

## Использование связного списка на практике

В чистом виде связный список в продакшен-коде используется **редко** из-за плохой локальности и промахов кэша.

### Но связанный список — фундаментальная структура

Он служит основой для других структур данных:

**Пример: Unrolled Linked List (связанный список массивов)**

Каждый узел хранит не один элемент, а **массив элементов** (например, по 64 штуки). Это даёт:

- Лучшую локальность (в кэш попадает целый массив элементов)
- Меньше накладных расходов на указатели (узлов меньше)
- Рост без копирования (новый узел просто добавляется в список)

**Бенчмарк unrolled linked list:** разница с массивом всего 10-15%, а не 2x.

## Когда что использовать

| Сценарий                                          | Лучшая структура                 | Почему                                                  |
|---------------------------------------------------|----------------------------------|---------------------------------------------------------|
| **Размер известен заранее**                       | Массив                           | Максимальная производительность, нет накладных расходов |
| **Нужен быстрый доступ по индексу**               | Массив                           | O(1) против O(n)                                        |
| **Частые вставки/удаления в середине**            | Связный список                   | O(1) против O(n)                                        |
| **Частое добавление в конец (особенно с ростом)** | Вектор (амортизированный массив) | Амортизированная O(1)                                   |
| **Частое добавление в начало или оба конца**      | Кольцевой буфер / Дек            | O(1) для обоих концов                                   |
| **Непрерывный рост без копирования**              | Unrolled linked list             | Нет релокаций, хорошая локальность                      |
| **Встраиваемая система без динамической памяти**  | Фиксированный кольцевой буфер    | Предсказуемость, нет аллокаций                          |

## Идеальной структуры данных не существует

**Главный вывод лекции:** не существует структуры данных, которая была бы лучшей во всех ситуациях. Всегда есть
компромисс:

- **Массив** — быстрый доступ по индексу, хорошая локальность, но дорогие вставки/удаления
- **Связный список** — быстрые вставки/удаления, нет релокаций, но медленный доступ и плохая локальность
- **Кольцевой буфер** — хорош для очереди, но расходует память при добавлении в один конец
- **Unrolled linked list** — гибрид, лучше локальности чистого списка, но сложнее

Задача инженера — проанализировать кейс и выбрать наиболее подходящее решение.

## Итоги лекции

### Ключевые выводы

1. **Абстрактные структуры данных** (стек, очередь, дек) — это контракты, а не реализации. Их можно реализовывать
   по-разному.

2. **Стек и очередь** — важнейшие АСД. Они лежат в основе вызовов функций, парсинга, алгоритмов на графах, обработки
   запросов.

3. **Дек (двусторонняя очередь)** — добавляет операции на оба конца. Массив в JS поддерживает дек через
   `push/pop/unshift/shift`.

4. **Проблема очереди на массиве** — `shift` сдвигает все элементы O(n). Решения:
  - Два указателя со вставкой в середину (хорошая локальность, половина памяти)
  - Кольцевой буфер (полное использование памяти, чуть хуже локальность)

5. **Связный список** — решение проблемы копирования, но создаёт проблему локальности данных (медленнее массива в 2x).

6. **В чистом виде связный список в промышленной разработке используется редко** из-за проблем с кэшем.

7. **Гибриды** — unrolled linked list (связанный список массивов) — чинят локальность, сохраняя преимущества роста без
   копирования.
