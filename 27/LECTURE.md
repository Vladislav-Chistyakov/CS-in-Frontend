# AI конспект для лекции #27

## Введение: синхронный порядок исполнения

В традиционной синхронной модели инструкции выполняются одна за другой в том порядке, в котором они записаны. Если
встречается операция, требующая времени (например, чтение с диска или сетевой запрос), программа останавливается и ждёт
завершения. Это называется **блокировкой потока исполнения**.

```javascript
// Синхронный пример (блокирующий)
const data = readFileSync("file.txt");  // программа стоит здесь
console.log(data);                      // выполнится только после чтения
console.log("Это сообщение ждёт");
```

Этот подход прост для понимания, но создаёт проблему: программа перестаёт реагировать на пользователя во время ожидания.

## Обработка событий с неопределённым временем срабатывания

В реальном мире события происходят непредсказуемо: клик мыши, ответ от сервера, таймер. Программа должна уметь
обрабатывать такие события, не останавливая основной поток. Это привело к появлению нескольких архитектурных решений.

## Блокировка потока исполнения и её последствия

Когда поток блокируется, он не может делать ничего другого. В синхронном однопоточном приложении это означает, что
интерфейс пользователя «замерзает»:

- не обрабатываются клики;
- не перерисовывается интерфейс;
- не срабатывают таймеры.

Человек воспринимает задержку более 100 мс как «тормоз», а более 300 мс — как зависание.

## Интерактивность и производительность

Современные пользовательские интерфейсы требуют **отзывчивости** (responsiveness):

- время реакции на ввод — не более 50–100 мс;
- частота кадров анимации — 60 FPS (каждый кадр не более 16.6 мс);
- длительные операции не должны блокировать основной поток.

Этого можно достичь разными способами.

## Модели реализации неблокирующего поведения

### Реализация на основе многопоточности

Классический подход: для длительных операций создаются отдельные потоки. Пока один поток ждёт ответа от сервера, другие
продолжают работу.

**Преимущества:**

- естественная модель (один поток = одна последовательная задача);
- возможность использовать несколько ядер процессора.

**Недостатки:**

- переключение контекста дорого;
- состояние гонки (race conditions);
- блокировки (deadlocks, livelocks);
- высокая сложность отладки.

### Зелёные потоки

Зелёные потоки (green threads, виртуальные потоки) — это потоки, которые реализованы не ядром ОС, а рантаймом языка. Они
легче: тысячи зелёных потоков могут работать внутри одного потока ОС.

**Примеры:** Go (горутины), Erlang, Java (виртуальные потоки Project Loom), ранний Ruby.

**Как работают:** рантайм сам переключается между зелёными потоками в точках, где текущий поток мог бы заблокироваться (
например, при вводе-выводе). Внешне код выглядит как синхронный, но по факту блокировки нет.

```go
// Go: горутины выглядят синхронно, но работают конкурентно
data, err := http.Get("https://example.com")
// пока один горутина ждёт, рантайм переключит на другую
```

### Асинхронный подход

Асинхронный подход основан на **неблокирующих операциях** и **колбэках**. Вместо ожидания операция запускается, а когда
она завершится — выполняется переданная функция.

```javascript
// Асинхронный неблокирующий пример
fs.readFile("file.txt", (err, data) => {
    console.log(data);  // выполнится когда файл прочитается
});
console.log("Это сообщение не ждёт");  // выполнится сразу
```

Код не блокируется, но колбэки порождают проблему «ада обратных вызовов» (callback hell), когда вызовы вкладываются друг
в друга.

### Промисы и современная инфраструктура

**Промисы (Promises)** — это абстракция над асинхронной операцией, которая может находиться в трёх состояниях:

- `pending` — ожидание;
- `fulfilled` — успешно завершена с результатом;
- `rejected` — завершена с ошибкой.

Промисы позволяют выстраивать цепочки:

```javascript
fetch("/api/user")
    .then(response => response.json())
    .then(user => fetch(`/api/posts/${user.id}`))
    .then(response => response.json())
    .then(posts => console.log(posts))
    .catch(error => console.error(error));
```

С появлением `async/await` асинхронный код стал выглядеть почти как синхронный, но без блокировок:

```javascript
async function getUserPosts() {
    try {
        const user = await fetch("/api/user").then(r => r.json());
        const posts = await fetch(`/api/posts/${user.id}`).then(r => r.json());
        console.log(posts);
    } catch (error) {
        console.error(error);
    }
}
```

### Когда асинхронность не нужна

Асинхронность не является серебряной пулей. Она не нужна, когда:

- все операции выполняются быстро (десятки микросекунд);
- нет ввода-вывода или ожидания внешних событий;
- задача является чисто вычислительной и полностью загружает процессор — здесь асинхронность не поможет, потому что нет
  моментов для переключения.

Тяжёлые вычислительные задачи (обработка изображений, шифрование, свёртки нейросетей) лучше выносить в отдельные потоки
или воркеры, либо передавать на GPU.

## Откуда берутся setTimeout и подобные функции

Функции вроде `setTimeout`, `setInterval`, функции для работы с файлами и сетью — это не часть самого JavaScript. Они
предоставляются **окружением** (хост-средой):

- в браузере — Web API (объекты `window`, `document`, `fetch`, `setTimeout`);
- в Node.js — библиотеки `fs`, `http`, `crypto`, `timers`.

Сам JavaScript (спецификация ECMAScript) описывает только язык: типы данных, объекты, функции, управляющие конструкции.
Асинхронные операции — это расширения, предоставляемые хост-средой.

## Агенты в спецификации JavaScript

В спецификации ECMAScript есть понятие **агента (Agent)** — это единица выполнения, которая содержит:

- стек вызовов (call stack);
- глобальный объект;
- очередь задач (job queue);
- изолированную кучу (все объекты агента недоступны другим агентам без специальных механизмов).

В браузере каждая вкладка (или часть вкладки, как iframe с разными origin) — это отдельный агент. Веб-воркеры (Web
Workers) — тоже отдельные агенты. Агенты **не разделяют память** по умолчанию (только через `SharedArrayBuffer` с
атомиками).

Один агент всегда однопоточен — внутри агента никогда не происходит одновременного выполнения двух кусков
JavaScript-кода.

---

## Асинхронность ≠ параллельность

Это ключевое различие, которое часто путают.

- **Асинхронность** — про режим ожидания: задача не блокирует выполнение других задач. Поток может быть всего один.
- **Параллельность** — про одновременное выполнение на нескольких ядрах или процессорах.

Асинхронный код может быть параллельным (если задействует несколько потоков/воркеров), но чаще всего он работает в одном
потоке. В JavaScript асинхронность достигается **без параллельности** внутри одного агента.

```javascript
// Асинхронно, но не параллельно
setTimeout(() => console.log("A"), 0);
setTimeout(() => console.log("B"), 0);
console.log("C");
// Вывод: C, A, B — всё в одном потоке
```

### Когда потоки полезны (даже в JS)

Несмотря на однопоточность агента, в JavaScript есть способы задействовать несколько ядер:

- **Web Workers** (браузер) — выполняют код в отдельном агенте с изолированной памятью.
- **Worker Threads** (Node.js) — аналогично.
- **`SharedArrayBuffer`** — разделяемая память между агентами (требует атомарных операций).

Потоки полезны для:

- тяжёлых вычислительных задач (поиск, шифрование, обработка изображений);
- использования всех ядер процессора;
- изоляции ненадёжного кода.

## Параллельные запросы, последовательные колбэки

Важное различие: хотя JavaScript-код в одном агенте никогда не выполняется параллельно, **хостовые операции** (например,
сетевые запросы, работа с файловой системой, таймеры) выполняются вне основного потока. Это значит, что несколько
запросов могут быть отправлены одновременно и ждать ответа параллельно.

Когда мы пишем:

```javascript
fetch("/api/user")
fetch("/api/posts")
fetch("/api/comments")
```

Браузер или Node.js отправляет три HTTP-запроса **одновременно**, не дожидаясь завершения каждого. Параллелится не
выполнение JavaScript-колбэков, а сами операции ввода-вывода.

Однако колбэки, которые будут вызваны при получении ответов, всё равно попадают в очередь макрозадач и обрабатываются
событийным циклом **последовательно** (по одному).

## Реальный пример параллельного кода в JS

В стандартном однопоточном асинхронном JS невозможно выполнять два куска кода одновременно в одном агенте. Но можно
запустить несколько воркеров:

```javascript
// main.js
const worker1 = new Worker("worker.js");
const worker2 = new Worker("worker.js");

worker1.postMessage({task: "heavy", data: bigArray1});
worker2.postMessage({task: "heavy", data: bigArray2});

Promise.all([
    new Promise(resolve => worker1.onmessage = resolve),
    new Promise(resolve => worker2.onmessage = resolve)
]).then(results => {
    console.log("Оба воркера завершили работу");
});
```

## Event Loop браузера: схема работы

**Событийный цикл (Event Loop)** — это бесконечный цикл, который поддерживает очередь задач и решает, когда выполнять
JavaScript-код. Он основан на модели **кооперативной многозадачности** на уровне задач.

Упрощённая схема:

1. Извлечь **одну макрозадачу** из очереди макрозадач.
2. Выполнить её полностью (от начала до конца).
3. Выполнить **все микрозадачи** из очереди микрозадач (каждая выполняется полностью, пока очередь не опустеет).
4. По возможности — выполнить рендер (перерисовку страницы).
5. Перейти к шагу 1.

### Макрозадачи (Task)

Макрозадача — это атомарная единица работы, которая выполняется целиком, прежде чем событийный цикл переключится на
другую макрозадачу или рендер.

Примеры источников макрозадач:

- обработчики событий (`onclick`, `onload`);
- колбэки `setTimeout`, `setInterval`;
- сетевые колбэки (`fetch`, `XMLHttpRequest`);
- колбэки `requestAnimationFrame` (частично, зависит от браузера).

### Микрозадачи (Microtask / Job)

Микрозадачи — это более приоритетные задачи, которые выполняются **после завершения текущей макрозадачи, но до рендера и
до следующей макрозадачи**.

Источники микрозадач:

- колбэки промисов (`.then`, `.catch`, `.finally`);
- `queueMicrotask`;
- `MutationObserver`;
- `async/await` (продолжение после `await`).

### Правило: одна макрозадача — все микрозадачи

Это фундаментальное правило событийного цикла:

> После завершения выполнения текущей макрозадачи, прежде чем взять следующую макрозадачу или обновить рендер, *
*выполняются все накопившиеся микрозадачи**.

```javascript
setTimeout(() => console.log("A"));      // макрозадача
Promise.resolve().then(() => console.log("B")); // микрозадача
console.log("C");                        // синхронный код в текущей макрозадаче

// Вывод: C, B, A
// Потому что:
// 1. Текущая макрозадача (основной скрипт) завершается.
// 2. Выполняются все микрозадачи (B).
// 3. Берется следующая макрозадача (A).
```

## Обработка микрозадач

Микрозадачи обрабатываются специальным алгоритмом:

- После завершения каждой макрозадачи.
- Если микрозадача порождает новую микрозадачу, она будет выполнена в том же цикле (очередь микрозадач не пустеет).
- Если микрозадач слишком много, они могут «задушить» макрозадачи и рендер, вызывая зависание интерфейса.

```javascript
function infiniteMicrotasks() {
    Promise.resolve().then(() => {
        // Бесконечно добавляем новые микрозадачи
        infiniteMicrotasks();
    });
}

infiniteMicrotasks();
// Рендер никогда не произойдёт, макрозадачи не будут обработаны
```

## Зачем нужны микрозадачи

Микрозадачи решают несколько важных проблем:

1. **Согласованность состояния** — дают возможность выполнить колбэки промисов до того, как браузер выполнит рендер,
   сохраняя промежуточное состояние внутри одного логического шага.
2. **Снижение задержек** — микрозадачи выполняются сразу после текущей макрозадачи, без ожидания следующей итерации
   цикла.
3. **Избежание избыточного рендеринга** — если несколько промисов вызывают изменения DOM, они могут выполниться до
   рендера, объединив изменения.

## API планировщика (scheduler)

Современные браузеры предоставляют API для более тонкого управления приоритетами задач — **Scheduler API** (пока не
везде, но развивается).

### Приоритеты:

- **`user-blocking`** — задачи, которые влияют на взаимодействие с пользователем (высший приоритет, выполняются без
  задержки).
- **`user-visible`** — задачи, которые видны пользователю, но не блокируют интерфейс (средний приоритет).
- **`background`** — фоновые задачи (низкий приоритет, могут откладываться).

```javascript
// Пример (условный, API развивается)
scheduler.postTask(() => {
    console.log("Высокий приоритет");
}, {priority: "user-blocking"});

scheduler.postTask(() => {
    console.log("Низкий приоритет, фон");
}, {priority: "background"});
```

### requestAnimationFrame (RAF)

`requestAnimationFrame` — это специальный механизм для выполнения анимаций. Колбэки RAF выполняются **перед рендером** (
но после микрозадач), что позволяет синхронизировать изменения с частотой обновления экрана (обычно 60 FPS).

```javascript
let start = null;

function animate(timestamp) {
    if (!start) start = timestamp;
    const progress = timestamp - start;
    element.style.transform = `translateX(${Math.min(progress, 200)}px)`;
    if (progress < 200) {
        requestAnimationFrame(animate);
    }
}

requestAnimationFrame(animate);
```

**Порядок в браузерном событийном цикле:**

1. Одна макрозадача
2. Все микрозадачи
3. Изменения DOM и стилей
4. `requestAnimationFrame` колбэки
5. Рендер (отрисовка кадра)
6. `requestIdleCallback` колбэки (если есть время)

### Кооперативная многозадачность через scheduler.yield

`await scheduler.yield()` (экспериментальный API) позволяет добровольно вернуть управление событийному циклу, не
дожидаясь конца текущей задачи. Это даёт настоящую **кооперативную многозадачность** на уровне пользовательского кода.

```javascript
async function heavyTask() {
    for (let i = 0; i < 1000000; i++) {
        // Выполняем итерацию
        if (i % 1000 === 0) {
            // Добровольно отдаём управление, позволяя рендеру и другим задачам выполниться
            await scheduler.yield();
        }
    }
}
```

## Пример разбиения тяжёлой задачи

Без кооперативной модели долгая синхронная операция заблокирует поток:

```javascript
// Плохо: блокирует поток на секунды
function heavySync() {
    for (let i = 0; i < 1e9; i++) {
      // что-то вычисляем
    }
}
```

Решения:

1. **Разбиение через `setTimeout` (макрозадачи)** — неэффективно, вносит большие задержки.
2. **Разбиение через `queueMicrotask`** — неправильно, микрозадачи не дают рендеру.
3. **Разбиение через `scheduler.yield`** — оптимально (современный способ).
4. **Перенос в Web Worker** — для действительно тяжёлых задач.

```javascript
// Разбиение через setTimeout (классический способ, но с задержками)
async function processInChunks(array, chunkSize, callback) {
    let index = 0;

    function processChunk() {
        const end = Math.min(index + chunkSize, array.length);
        for (; index < end; index++) {
            callback(array[index]);
        }
        if (index < array.length) {
            setTimeout(processChunk, 0); // отдаём управление
        }
    }

    processChunk();
}
```

## Эволюция Event Loop в браузерах

Событийный цикл развивался вместе с браузерами:

- **Ранние браузеры** — простая очередь макрозадач.
- **Появление промисов** — внедрение микрозадач (Jobs) как отдельной очереди.
- **Современные браузеры** — разделение задач по приоритетам, интеграция с рендером, оптимизация для анимаций.
- **Будущее** — Scheduler API, приоритеты, кооперативная многозадачность на уровне языка.

## Event Loop в Node.js

Node.js использует похожую, но не идентичную модель из-за наличия собственного бэкенда (libuv).

**Фазы Event Loop в Node.js:**

1. **Timers** — выполнение колбэков `setTimeout` и `setInterval`.
2. **Pending callbacks** — колбэки завершённых операций ввода-вывода.
3. **Idle, prepare** — внутреннее использование.
4. **Poll** — получение новых событий ввода-вывода.
5. **Check** — выполнение колбэков `setImmediate`.
6. **Close callbacks** — закрытие соединений и сокетов.

Между фазами обрабатываются микрозадачи (из промисов и `process.nextTick` отдельно).

### Node.js: process.nextTick и setImmediate

**`process.nextTick`** — колбэк выполняется **перед продолжением текущей фазы**, фактически до любой макрозадачи и даже
до микрозадач промисов. Это самый высокий приоритет.

**`setImmediate`** — колбэк выполняется в фазе `Check` (после фазы `Poll`), то есть чуть позже, чем `nextTick`, но до
таймеров следующей итерации.

```javascript
console.log("A");

setTimeout(() => console.log("B"), 0);
setImmediate(() => console.log("C"));
process.nextTick(() => console.log("D"));
Promise.resolve().then(() => console.log("E"));

// В Node.js: A, D, E, B/C (B и C могут в разном порядке, зависит от фазы)
```

**Правило:** `process.nextTick` > микрозадачи промисов > `setImmediate` > `setTimeout` (при нулевой задержке — зависит
от фазы).

## Итоги лекции

- **Синхронный код** — простой, но блокирующий. Блокировка делает интерфейс неотзывчивым.
- **Асинхронность** позволяет не блокировать поток во время ожидания. В JavaScript асинхронность реализована через
  событийный цикл и очереди задач.
- **Промисы и async/await** — современный стандарт для работы с асинхронностью, заменяющий колбэки.
- **Событийный цикл** — основа выполнения в браузерах и Node.js. Он координирует макрозадачи, микрозадачи и рендер.
- **Микрозадачи** выполняются после каждой макрозадачи (все подряд) до рендера.
- **Асинхронность ≠ параллельность**. В одном агенте JS параллелизма нет — только кооперативная многозадачность на
  уровне задач.
- **Работы и воркеры** позволяют использовать несколько ядер процессора.
- **API планировщика и `scheduler.yield`** дают более тонкий контроль над приоритетами и кооперативной многозадачностью.
- **Event Loop Node.js** имеет дополнительные фазы и отдельные очереди для `nextTick` и `setImmediate`.
